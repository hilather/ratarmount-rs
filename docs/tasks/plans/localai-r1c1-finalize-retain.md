## 1. Goal

1. One `finalize_top`, shared by `sandbox run` and the supervisor, with `sandbox run`'s reports byte-identical and its error order (classify, gate, compose) kept.
2. A v2 `finalize {id, pack, request_id}` that stops an attempt without a lazy unmount, then fscks, seals under the top's overlay root flock with a deadline, hashes, optionally packs and reports. It answers `writers_active` while writers remain and is retry-safe under R1a's `request_id` (Keystone #6).
3. `new` with `retain: true` and a commit of the finalized attempt into `state/retained/ID`: durable before it is acknowledged, never deleted by a restart, usable within the run as a lower, and recorded with the identity R1c-2 needs (§5.7).
4. Durability owned by retain and finalize (ruling 1+2): every finalize, with or without `retain`, syncs the files and directories of every layer the attempt references, bundle cache entries included, after their publication completed; cache extraction never syncs.

**Boundaries stated for Keystone's attention:**
- **The base** (sweep 1, Claude N6; wording corrected in sweep 2, Codex N3). Ruling 1+2 enumerates layers ("the layer files, then the destination directory, then its parent"). The base is not a layer: it is the registered source ratarmount never writes, prepared in place at `create_base`. It is not synced, and keeping it durable is the caller's job: the gates compare metadata only (stamps, weak manifests, tree ids; `overlay_meta.rs:1790-1795`), and a weak manifest is blind to a same-size change with a restored mtime (`:1629-1631`), so a lost base write with surviving metadata need not be refused (Risk 3).
- **`sandbox run`** (sweep 2, Claude N5). "Finalize" in the ruling is the supervisor's `finalize` operation, the one R1c defines (source doc `:111-120`). `sandbox run` shares `finalize_top` because the source doc factors it out of `sandbox run` (`:111`), but it is not that operation and retains nothing, and source test 10 holds its reports and behaviour unchanged, so S is not added to it. If Keystone wants `sandbox run` synced too, it is the same S over its top and lowers.

## 5. Design

### 5.1 Protocol

- **v2 `new`** gains `retain: bool` (`#[serde(default, skip_serializing_if = "is_false")]`). R1a's `defaults()` (`requests.rs:332-342`, with R1b's `lowers`) gains `("retain", false)`, so R1a's golden digest (U5) is unchanged. R1b's routing rule becomes: a v2 `new` without `request_id`, `lowers`, `journal` or `retain` has the v1 form.
- **v2 `finalize {id, pack = false, request_id?}`**, `deny_unknown_fields` through the enum; `request_id` uses R1b's string-only `some` deserializer (`null` refused). `defaults()` gains `("pack", false)` for `finalize`; `id` is hashed.
- **v1** is untouched: `finalize` and `retain` stay `invalid_request` (R1a U1).
- **v2 `list`** returns the attempts, then the retained entries of this run (§5.7), each with the v1 attempt shape. v1 `list` keeps its code over the attempts map.
- **New codes:** `writers_active` (v2 `finalize` only) and `retained` (`destroy {id}` of a retained ID, v1 and v2 alike, reachable only after a v2 client retained). Existing codes keep their meaning: `lower_changed` (R1b) for a changed recorded lower, `in_use` for a busy lower, `capacity`, `io`.
- **Statuses:** `finalizing` (finalize started and has not finished; resumable) and `finalized` live in the attempts map and are visible in v1 `list` once a v2 client finalizes; `retained` appears only in v2 `list`.

### 5.2 One durable-log engine (the requirement, and its premise)

**Premise.** The request names "the ONE shared fsync/compaction helper used by requests.jsonl (R1a) and the R1b journal". Only R1a has one; R1b's journal is the child-written `OpLog` file (row 7). R1c-1 leaves `OpLog` alone and makes the journal durable at retain, like every other file the retained attempt references (§5.6).

**Extract, never copy.** Step 1 moves R1a's record-independent mechanics from `RequestLog` into `ratarmount/src/sandbox/state_log.rs` as `StateLog<R: Records>`: the checked open, the open-time file and directory syncs, the bounded streaming replay with torn-tail truncation and damage refusal, the leftover sweep, append-then-`sync_data` with truncation, `Broken`, verbatim compaction with backoff, fault points and events, and `sync_dir`. `Records` supplies parsing, applying, the live lines in file order, live bytes, the compaction precondition and the file's messages. `RequestLog` becomes `StateLog<RequestRecords>`; the record rules (eviction, reservation, `op_hash`) stay in `requests.rs`. Every name R1a's tests use stays (`faults`, `events`, `line_high_water`, `live_lines()`, `is_broken()`, `status()`, `descriptor()`, `TEST_FAULTS`, `TEST_LIMITS`, `BEFORE_OUTCOME`), messages keep their text, and each instance has its own fault queue and events, so R1a's suite and its event assertions (`requests_tests.rs:497`, `:630-640`) run unchanged. `retained.jsonl` is `StateLog<RetainedRecords>`. Every directory fsync R1c-1 needs (the logs, the retained tree's parents, lower parents) goes through that `sync_dir`; files are synced through the managed cursor (§5.6). No `syncfs`, and no second log or fsync helper.

**Finalize request records** live in `requests.jsonl` as `v: 1` lines with `op: "finalize"` and exactly R1a's members per state: `running` and `retryable` carry none, `done` carries `attempts: [ID]` and `result`, `failed` carries `attempts` and `error`. R1a made `op` the kind (`requests.rs:146`; R1a plan `:129`) and planned for older daemons refusing an unknown `op` (R1a plan `:403`); the members per state, which are the line schema `:159` versions, do not change, so `v` stays 1. Code changes: `Kind` gains `Finalize`; `parse_line` accepts it; `encode_line`, `done_line`, `begin` and `finish` take the kind; a `Record` keeps its kind so `resolve_interrupted` writes the finalize message ("finalize was cut off by a supervisor restart before it finished; an attempt that was not retained was discarded, and a retained one is kept on disk"); `stored()` is unchanged. Every finalize error is `retryable` (nothing needs undoing; a retry resumes, §5.4); a `done` line's `attempts` reserves the ID while the record lives (R1a §5.6). Only a restart writes `failed`.

**`retained.jsonl`** (0600, owned, one link, opened like `requests.jsonl`), one record per attempt ID:

```text
{"v":1,"id":"attempt-a1B2c3","t":"retained","base":"task","layer_digest":"sha256:…","sealed_at":"…","prefix":[{"path":"…","layer_digest":"sha256:…","sealed_at":"…"}],"over":["attempt-z9Y8x7"],"paths":{"overlay":"…/retained/attempt-a1B2c3/overlay","bundle":null},"report":{…}}
{"v":1,"id":"attempt-a1B2c3","t":"aborted"}
```

A record is live while its last line is `retained`; `aborted` ends it and compaction drops it. There is no eviction; `--max-retained` bounds the live set. The line bound is 16 KiB (a report of about 3 KiB plus at most 32 prefix records), so the engine keeps at most 256 MiB in memory at the 16,384 cap and about 12 MiB at the default 4,096. `new` with `retain` measures that line before any attempt exists (§5.5, sweep 1 Claude N5); the same check at the commit is only a backstop. Damage before the last line refuses the start with this log's own advice ("moving it aside keeps every `retained/` tree; the records restart recovery reads are lost").

### 5.3 `finalize_top` (new `ratarmount/src/sandbox/finalize.rs`)

One function, called by `sandbox run`'s `finish` and by the supervisor. The caller passes: the top; a **classify** callback (given the top's `OverlayMeta`, returns the `ClassifiedBase`); a **compose** callback (given the classified base's source, returns the view the layer is sealed and hashed over); an optional supplied base digest; whether to seal, with an `Option<Instant>` deadline for the root flock (`None` is `sandbox run`'s unbounded acquire; the supervisor passes `Some` from step 3 on, so step 2b adds no variant without a production user; sweep 2 Claude N7); whether to pack (the bundle path and the journal to include); the manifest and journal-summary paths; and a **`&mut FinalizeProgress`** that `finalize_top` updates as each phase completes, so it survives an error from a later phase (sweep 1 Codex B2). In R1c-1 it holds `packed`, set the moment `pack` returns `Ok`; a try that finds it set skips phase 3. `sandbox run` passes a fresh one; the supervisor keeps one per attempt. It returns the fsck result, the canonical hash and change count, the meta-derived `patch_hash` fields, the manifest path, the journal summary and the bundle path, which is what `sandbox run`'s report reads (`run.rs:1186-1192`); step 3 adds the seal outcome (`layer_digest`, `sealed_at`) with the supervisor, its only reader, so step 2b leaves no field unread (sweep 3 Claude N2).

Phases, in `sandbox run`'s order (row 3):

1. **fsck**: `fsck(top, repair = !sealed)`; a top sealed by an earlier try is checked read-only (row 5). It must be clean. This phase is its own function and `FinalizeProgress` is the place its first `repaired:N` will be kept (the R1c-2 seam for partial fsck progress); R1c-1 reports the current try's result.
2. **Classify, gate, compose, seal.** When sealing: `SealOperation::acquire` or `acquire_until` (`WouldBlock` at the deadline), then `finish_if_sealed`; under the flock, `OverlayMeta::read`, **classify**, **`gate_base`** with `force_base_mismatch: false`, **then compose**, then `SealOperation::seal`, which consumes the guard. A top sealed by an earlier try is still classified, gated and composed (pack and hash need the view). Without sealing: classify, gate, compose, no lock. Gating before composing keeps today's errors: a changed base is refused with the gate's text before any bundle lower is copied or verified (Codex note; T1).
3. **Pack** unless `progress.packed`, with the base still open (`include_journal` when there is a journal); `progress.packed` is set as soon as it returns `Ok`, before phase 4 can fail, so a retry never packs onto its own bundle (row 20).
4. **Hash and outputs**: `change_set` and `canonical_hash` with `Normalize::Strict`, unchanged; the manifest and journal summary (both overwritten); `OverlayMeta::read`.

`sandbox run` keeps its classification (`classify_base(Some(&args.base), …)`), its `compose` of `args.lower`, no deadline, its sidecar paths and `--base-digest`, and builds today's JSON from the result plus its own fields; `ProgressToStderr` stays around its call in `run.rs`, because it redirects the whole process's fd 1 (`diff.rs:217-249`). Classification moves under the root flock when sealing, which is `SealOperation`'s contract (`overlay_seal.rs:335-336`) and changes no report byte.

**`acquire_until(dir, deadline: Option<Instant>)`**: `SealCommitGuard::acquire_until(dir, deadline)`, with `acquire` as `acquire_until(dir, None)`, unchanged; `SealOperation::acquire_until(dir, deadline)` of the same shape beside `acquire`, which `finalize_top` calls with the caller's deadline; the stub twin returns the same `unsupported` error.

The status becomes `finalizing` once step 4 returns `Stopped` or `Detaching`, and `finalized` (or `retained`) at the end. A failure leaves the attempt resumable; a `finalized` attempt keeps its report and its `--max-attempts` slot until `destroy`.

**Stop** (`Mounter::stop(attempt, FINALIZE_WAIT)`, decided by the kernel, no namespace scan):
1. If `attempt.path` is mounted, run `<binary> -u -- PATH` (`ratarmount_fuse::unmount`: non-lazy, about 1 s of busy retries), bounded at 3 s by `wait_bounded`, which kills and reaps the helper at the bound. Still mounted: **`Busy`**; nothing else changes, the status stays `ready` (or `crashed`) and the attempt stays mounted (Keystone #6). A `fusermount3` the killed helper started may still unmount later; that is harmless, because every try decides from the mount table again.
2. Whether to wait for a child comes from `ProcessMounter`'s child registry, never from the status (a `crashed` attempt can have a live child, row 10). A recorded child is waited for without a signal, up to `FINALIZE_WAIT = min(--timeout, 10 s)`. Exited: **`Stopped { exit }`**. `ProcessMounter` keeps every reaped child's `ExitStatus` until `cleanup`, from `poll` (which today drops it, `process.rs:205-207`) and from `stop`, so a child `supervise()` reaped earlier still reports its status; none ever recorded is `Stopped { exit: None }`, which step 4b treats as unclean. Still alive: **`Detaching`** (another mount of the superblock keeps the child serving; `writers_active` with "the mount process has not exited after the unmount; another mount namespace may hold the attempt; retry").

`Busy` and `Detaching` give `writers_active`; nothing is sealed. Writes reach the overlay only through the child, so seal never runs while a FUSE writer can exist. A retry of an attempt a previous try left `Detaching` checks its child once with `try_wait` and does not wait again (sweep 1 Claude N2). Each `Busy` answer still costs the serial daemon up to the helper's 3 s, and the first `Detaching` answer up to `FINALIZE_WAIT`; the docs tell harnesses to stop their container before finalizing and to back off (§5.12). `Detaching` is what a premature finalize of a Docker attempt gets: `docker run -v` gives the container its own copy of the mount, so the daemon's unmount removes only the host mount, and the attempt's path is gone for the harness while the container keeps writing through the child; once the container stops, a retry seals those writes too (sweep 1 Claude N3). `stop` never runs `-z`, `umount -l` or a signal to the FUSE child; `destroy` keeps `cleanup`'s kill-and-lazy policy, also for `finalizing` attempts. `supervise()` polls only `starting` and `ready`. `deleted_paths` keeps today's rule for the v1 statuses (the inspection socket for `starting` and `ready`, the offline database for `crashed`, `process.rs:216-223`), and for a `finalizing` attempt uses the socket while its child is alive (after a `Detaching` answer the child still holds its overlay database exclusively, `docs/sandbox.md:2474-2476`), the offline database once it exited, so `diff` and `stats` keep working in between (sweep 4 Claude N4).

**`status` inspection command.** `inspection::start` also takes the child's `Option<Arc<OverlayQuota>>` (`main.rs:2641`); `status` upgrades the overlay first, like `deleted_paths`, and answers one JSON line `{"erofs_denied":N}` from `quota.usage().erofs_denied` (`QuotaUsage`, `overlay_policy.rs:432-438`; 0 without a policy). R1b's client reads one newline-terminated JSON value (`r1b-impl inspection.rs:139-180`), which the multi-line `status_text()` is not (sweep 4 Claude N1, Codex N3), so the reply is structured and the client decodes it as such. A dropped overlay ends the connection without an answer, and the client reports an error.

**Report** (source doc `:118`): `status`, `attempt` (`{id, base, path, overlay_dir, status}` with final paths), `patch_hash` (as `sandbox run`'s, which carries `stack` and `base_digest_state`), `layer_digest`, `stack_digest`, `fsck_result`, `bytes_written`, `erofs_denied`, `manifest_path`, `journal_summary`, `bundle`. A retained report names `retained/ID/…` paths.

**Request IDs (Keystone #6).** The same ID and body re-run until `done`; a `done` record replays its report byte for byte without touching the attempt; another body (`pack` flipped, another `id`) is `idempotency_conflict` in every state. Without an ID, the fast path makes a repeated finalize safe.

### 5.5 Scope preflight (ruling 4 and the base rule)

One check, run at `new` with `retain: true` after the capacity and policy checks and before R1b's lower validation (only the retained record preflight below runs right after that validation, since it needs the canonical lower paths), always before `ram_root()`, R1a's request record preflight, any attempt directory or spawn; and at `finalize` step 2, before the stop. Every refusal is `invalid_request` naming the base, except the `retain`-only codes below:

- **Base rule:** no `binds`, not `recursive`, a source that is an absolute path or a `git:///` URL (R1b's private `check_base`, `r1b-impl lowers.rs:171-192`, made `pub(crate)` in step 3 and given the operation's name for its messages, so a refusal says "finalize" or "retain", not "lowers"; sweep 3 Claude N5), and no `git_synthetic_head` ("register the base without `git_synthetic_head` to finalize or retain it"; row 15).
- **Archive rule (ruling 4):** a source that is a regular file must have a prepared index, found by `ratarmount_index::resolve_prepared_index_location(source, None, &[state/indexes/<base>])` and opened with `SqliteIndex::open_lookup` (which creates nothing), whose `backend_name()` is `Some("SQLiteIndexedTar")` (`ratarmount_formats_tar::BACKEND_NAME`), as plain and compressed TAR (`.tar.zst`, `.tar.gz`, the documented sandbox base, `docs/sandbox.md:26`) both record: "base X is indexed by ZipMountSource, not as a TAR archive; finalize and retain support TAR archives only". An index with no `backendName` (a single compressed file, `factory_prepared_tests.rs:346-354`) gets "base X has no TAR index; …", and a missing or unreadable index "base X has no prepared index; …" (sweep 3 Claude N3). Directory and Git sources need no index.
- **`retain` only:** `overlay: "tmpfs"` (the RAM overlay lives outside `attempts/ID`, `daemon.rs:834-836`, so the commit rename would not move it); `capacity` past `--max-retained` (§5.7); `io` while `retained.jsonl` is `Broken`; and the **record preflight** (sweep 1 Claude N5), modelled on `record_preflight` (`daemon.rs:676-709`): the `retained.jsonl` line an attempt of the batch would write is measured with the real state paths, R1b's canonical lower paths, a bundle position's cache path at its fixed length (the cache root, canonicalized as the child canonicalizes the path it records, `ratarmount-compositing/src/lower_stack.rs:173-175`, through its deepest existing ancestor when it does not exist yet, plus 64 hex digits; sweep 2 Claude N3), a full `over` and a report with every field at its widest, and over 16 KiB the request is `capacity` before any attempt exists.

v1 is unchanged: `create_base` and v1 `new`, `list`, `diff`, `stats` and `destroy` behave as today on every base.

### 5.6 Durability in every finalize, and the retain commit (ruling 1+2)

**Step S runs in every finalize** (ruling 1+2 as written; sweep 1 Codex B3): every try of every finalize, with or without `retain`, after `finalize_top` succeeded and before its report is returned or its commit starts, whether its bundle lowers were fresh fills or cache hits and whatever built a cache entry. Nothing is skipped because an earlier finalize already synced an entry, and there is no generation marker. Only R1a's replay of a `done` record and the fast path for an attempt already `finalized` or `retained` return the stored report without running anything (R1a's replay is unchanged). That is a property, not a shortcut: S completed before that report was first returned, and since then the attempt is sealed and unmounted, its child is gone and its layers are immutable, so nothing it references can have become dirty; a second S would fsync clean inodes only. The child has exited and nothing is mounted at `attempts/ID/mnt`. S, in order:

1. **Each lower the child took** (R1b's records, bottom first): take the layer's **entry lock** (`overlay_pack::lock_layer_entry`: an exclusive `flock` on an `open_root` descriptor of the layer root, polled until `FINALIZE_WAIT`; `WouldBlock` → `in_use`). Under it, check that the layer root carries no write bit, for every lower however it was supplied (sweep 4 Codex B1): a cache entry left by a publisher killed between its rename and its restore can also be named as a directory lower, and R1b's directory read checks only the seal metadata (`r1b-impl lowers.rs:322-334`). Seal and `finalize_stage` both leave a root without write bits (row 12), and seal strips the root last, after its sentinel and its children (`overlay_seal.rs:546-551`), so a writable root is an unfinished publication, an interrupted seal, or a changed mode: `lower_changed` with the remedy ("lower X's root is writable, so it is not a completely published or sealed layer; run `ratarmount overlay seal X`, which finishes an interrupted seal or publication by restoring its sentinel and read-only modes, then retry"; sweep 4 Claude N5, corrected in sweep 5 Claude N2: `overlay seal` of a sealed layer runs `finish_recorded_seal`, `overlay_seal.rs:321-333`, while a `chmod a-w` of the root alone would leave an interrupted seal's children writable and its sentinel missing), nothing synced. This reverts sweep 3's bundle-only check (§9.9). Then `sync_tree(layer)`: every regular file, then every directory bottom-up, ending with the layer root; then `sync_dir(parent of the layer)`; release. This is "the layer files, then the destination directory, then its parent", for bundle cache entries and directory lowers alike. A file or directory the daemon cannot open fails the finalize with `io` naming the path (sweep 2 Claude N6). A lower on an intrinsically read-only image filesystem holds no dirty data: squashfs, erofs and iso9660 have no `fsync` method, so the kernel answers `EINVAL`. Only that case counts as synced: an fsync error whose `kind()` is `InvalidInput` on a path whose `statfs` type is squashfs (`0x73717368`), erofs (`0xE0F5E1E2`) or iso9660 (`0x9660`) (sweep 1 Claude N4). `EROFS` (`ReadOnlyFilesystem`) is never exempt and poisons like any other fsync error: ext4 answers it after aborting on an error and remounting read-only, when the data may be lost, and a `ST_RDONLY` flag cannot tell that apart from an image (sweep 5 Codex B1). The rule is on the kind, not the raw errno, because the managed cursor rebuilds an `xSync` failure as `io::Error::new(os.kind(), text)` with no raw errno (`managed_read.rs:675-677`), while `sync_dir` returns the raw errno, whose kind is the same (sweep 3 Claude N1, Codex N2). The type check is a Linux `statfs` beside `verify_tmpfs` in `daemon.rs` (`:934-950`), with a non-Linux twin that answers "not an image" (§5.10).
2. **The attempt's own tree** `attempts/ID`: `sync_tree` (the overlay payload and database, manifest, summary, journal, bundle, then the directories, ending with `attempts/ID`); for a tmpfs attempt also its `overlay_dir` (`ram/ID`, outside the tree), where an fsync costs nothing. **And the base's prepared state** `indexes/<base>/` (sweep 5 Claude N3): `sync_tree`, for every base kind. It is the daemon's own artifact, not the user's base: a retained layer over an archive can be mounted, or used as a lower, only through that index, since workers run `--no-recreate-index`; and nothing made it durable, because index builds run `synchronous = OFF` (`ratarmount-index/src/lib.rs:1346`), `publish_tmp` renames without syncing the directory (`:1997-1998`), and neither `finalize_prepared` nor `atomic_json` syncs `indexes/` or `indexes/<base>/`.
3. **Ancestors** (sweep 2 Codex B1): every directory above the lowers' parents, above `attempts/ID` and above `indexes/<base>/`, up to the root of the filesystem it is on (ascending while `symlink_metadata` reports the same `st_dev`), deduplicated and synced deepest first through `sync_dir`. A cache hierarchy that `cached_lower_in` created recursively (`$XDG_CACHE_HOME/ratarmount/layers`, `overlay_pack.rs:1909-1912`) is then durable from the entry up, and so is a state directory that `serve` created (`daemon.rs:1095`). No step decides which ancestors are new, so all of them are synced, and every level is strict (sweep 3 Codex B1): an ancestor that cannot be opened or synced, an unreadable one included (a write-and-search directory such as mode 0300 lets the recursive cache create add entries the daemon then cannot fsync), fails the finalize with `io` naming it, before the report or the `retained` record. Every ancestor of the state directory, the bundle cache and each lower, up to its filesystem's root, must therefore be readable by the daemon user (documented, §5.12).
4. **Without `retain`:** status `finalized` and the report. **With `retain`:** the commit R2–R5, whose R4 syncs the tree's new and old parents.

| # | Step of the commit (`retain` only) | On failure |
| --- | --- | --- |
| R1 | **S** (above) | `io`, nothing recorded or renamed; a failed fsync poisons its filesystem; an entry-lock deadline answers `in_use` and poisons nothing |
| R2 | Append the `retained` record (§5.2, §5.7) | engine truncation, else `Broken`; `io` |
| R3 | `rename_no_replace(attempts/ID → retained/ID)` on absolute paths (the two-directory form, §5.8). On success the entry and R1b's records leave the attempts map and `taken_lowers` at once and enter the retained map, not yet acknowledged, so memory always names where the tree is; the Mounter forgets the attempt's child entry and kept exit status (`Mounter::forget_child`, which unmounts and signals nothing; the child has exited), so `ProcessMounter`'s registry keeps no key for a path that has moved (sweep 5 Claude N7) | append `aborted`; `io`; status `finalizing`. A filesystem without `RENAME_NOREPLACE` answers `EINVAL` here on every try, after the whole finalize: the message says so (§5.8) |
| R4 | `sync_dir(retained/)`, then `sync_dir(attempts/)` (Keystone #2's parent-directory fsync; the state root and everything above it were synced in S, and the rename changes neither); the entry becomes `retained` | `io`; the entry stays unacknowledged, listed as `finalizing`. A failed fsync poisons the state filesystem (below), so this entry and every later finalize answer `io` until a restart; any other R4 error (an open failure) poisons nothing, and a retry of the finalize re-runs R4 and R5 |
| R5 | The request outcome `done` | R1a's `Broken` rules |

**The commit point** is the rename made durable by R4; the content (R1) and the record (R2) were durable before it. A crash before the rename leaves `attempts/ID`, which `reconcile` deletes (§5.8), and the request resolves to `interrupted` (Keystone #2). A stray `retained/ID` fails R3 with `EEXIST`; nothing is replaced. Every tree in `retained/` therefore has a live record, and a live record whose tree is not in `retained/` names a commit that never happened: R3's `aborted` line ends it when it can be written, and otherwise it stays live, reserving its ID and one slot, until R1c-2's recovery aborts it. `destroy` and `reconcile` delete a tree in `attempts/` as for any attempt. Nothing in R1c-1 deletes a tree in `retained/` (sweep 3 Claude N9): `destroy {id}` of any retained-map entry, an unacknowledged one included, is `retained`, so no crash can leave a partial tree that a live record names. An unacknowledged entry whose R4 cannot complete (its filesystem poisoned) stays listed as `finalizing` and refused as a lower until R1c-2's `forget`, or until an operator removes it with the daemon stopped (§5.13).

`sync_tree` fsyncs a regular file through `ManagedReadCursor::open(path)?.sync_all()` (row 13), so closing it never releases another connection's locks on an inode this process holds as a database (#151); it fsyncs a directory through `sync_dir`, which opens with `O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC` from step 3 on (sweep 2 Claude N9; today a plain `File::open`, `requests.rs:467`), so a FIFO or symlink put in a directory's place is refused instead of blocking the serial daemon in `open(2)`; does not follow symlinks (their entries are covered by the parent's fsync) and skips sockets such as a stale `inspect.sock`. It runs after `finalize_top` dropped its base view and layer connections.

**The entry lock on the cache side** (`overlay_pack.rs`, ruling 1+2's "per-entry publish/sync completion"):
- `publish_layer` takes the exclusive lock on the stage root's descriptor it already opens, before adding write permission and renaming, and releases it after the permission restore. The staged root and the published entry are one inode, so the lock covers the entry from the moment it is visible.
- **Publication must have completed, not merely released its lock** (sweep 1 Codex B1). A publisher killed between its rename and its restore releases the lock and leaves the root writable, and a restore that fails after the rename returns an error that today's lost-race fallback (`:1964-1969`) turns into an accepting `hit`. A completed publication leaves no write bit on the root (row 12), so that is the test, made under the lock.
- **A cache hit** (the existing-destination path `:1944-1946` and the lost-race path `:1968`) opens the destination with `open_root`, takes the lock shared (waiting), and holds it through its checks and verification until it returns the path (sweep 1 Codex N4). Its first check is the publication: if the root still has a write bit, the hit converts to exclusive, checks again, and finishes the restore the publisher did not (clears the write bits; only `publish_layer` adds one, and only `0o200`), then converts back to shared; if that fails, the entry is refused with an error and no caller gets its path. So no publish or S of that entry runs between a hit's wait and its return, a hit never returns a path whose publication had not completed, and hits of a complete entry, the common case, still run side by side. A conversion releases before it reacquires, and an entry only ever moves from incomplete to complete, so every interleaving ends with a sealed root. The hit's checks and verification take no flock of their own (`immutable_meta` and `overlay_seal::verify` open the layer through SQLite and take none), so the shared hold nests nothing.
- S, under its exclusive lock, refuses a lower with a writable root (above) rather than changing it.
- Cache extraction never syncs. An entry made by an older ratarmount was published without the lock or a sync; every finalize that references it syncs it, like any other entry.
- `publish_layer` is also `overlay unpack`'s publish (`overlay_pack.rs:1715`), so an unpack holds the same lock across its rename and permission restore; nothing else about unpack changes.
- A sealed layer root's `flock` is its #240 overlay root flock (row 2): the entry lock of a directory lower or a cache entry serializes with a seal, unseal or commit of that layer and with nothing else. S never holds two such locks; only `sandbox run` nests one, a cache hit's inside its top's, which cannot cycle (§5.9).

**Poisoning, by filesystem** (sweep 4 Codex B2). After an fsync error the kernel may have dropped the dirty data and reported the error once, so a later fsync can return 0 for lost data, and not only through the same name: the same inode reached as a hard link in another lower, or a shared directory (a cache's `layers/`, a common ancestor), syncs "successfully" afterwards. An error returned by any fsync in S or R4 therefore poisons, in memory, the whole filesystem it happened on (its `st_dev`). From then on, every S that would sync anything on that filesystem answers `io`, under any request ID or none ("a sync on the filesystem of PATH failed earlier in this daemon run, so its data may be lost; every finalize on it is refused until the daemon restarts, and a restart discards every unfinalized attempt; check the storage first"; sweep 5 Claude N6); the attempt that saw the error is therefore never finalized or retained in this run either. **How S checks** (sweep 5 Claude N1): before its first fsync, S stats every root it will walk (each lower root, `attempts/ID`, `indexes/<base>/`, and every S3 ancestor) and refuses if any is on a poisoned device; while walking, a directory on a poisoned device (a mount inside a layer) stops S at once, with nothing after it synced. A failed file fsync poisons the device of the file's directory as well as its own, because on stacked filesystems such as overlayfs without `xino` a file can report another `st_dev` than its directory, and S checks directories. An open or listing error, an entry-lock deadline, a writable lower root or the read-only image case above poisons nothing. Marks are not persisted: a restart starts with none (Risk 3).

### 5.7 Retained attempts: in a run, across a restart, and their identity (ruling 3)

- **The retained map** (this run): ID → the attempt with `retained/ID/…` paths, its report, R1b's records, its attempt state (`over` included), and whether R4 completed (acknowledged).
- **`list`**: v2 shows attempts and then retained entries in ID order; v1 is unchanged.
- **`diff`, `stats`** find an ID in the attempts map, then the retained map. A `finalized` or `retained` attempt is read offline; `diff` classifies its base (as §5.4 step 6) and runs `gate_base` with `force_base_mismatch: false`, which writes nothing, before composing the recorded layers; a gate refusal is `diff_failed` (the CLI `diff` gates too, `diff.rs:383-389`), and a failed open stays `base_open_failed`, as today.
- **`destroy {id}`** of a retained-map entry, acknowledged or not, is `retained` ("attempt ID is retained; retained attempts are never destroyed"; §5.6). `destroy {base}`, `shutdown` and `serve`'s final `destroy_all` (`daemon.rs:1155`) iterate the attempts map only.
- **The attempt's state** (sweep 3 Claude N8; one map since sweep 4, Claude N3 and Codex N4): the v1 `Attempt` shape has no room for it, and R1b keeps no per-attempt journal state (`r1b-impl daemon.rs:313-333`), so one side map `attempt_state: BTreeMap<String, AttemptState>` holds everything R1c-1 keeps per attempt: the plan (created with `retain`, with a journal, and `over`), written before the spawn; and the finalize state (`FinalizeProgress`, the first `bytes_written`, the last `erofs_denied`, the journal-failure mark of step 4b, the stored report). It is read by finalize, by S and by the `--max-retained` count; `destroy` removes it with the attempt, as it removes `taken_lowers` (`r1b-impl daemon.rs:1092-1103`), and the commit moves it into the retained entry. Nothing else is kept per attempt ID, so an ID drawn again starts clean. A journaled attempt whose `attempts/ID/journal.jsonl` is missing at finalize answers `io`, never "no journal".
- **As a lower** (R1b's reserved exception): the place rule accepts exactly `<state>/retained/<ID>/overlay` for an acknowledged entry of the retained map, matched lexically before any lookup, with `retained/`, `retained/ID` and `retained/ID/overlay` each a real directory (`symlink_metadata`, no symlink); then R1b's directory-lower checks apply unchanged (sealed, digest, stack and base agreement, re-check after ready). `retained/ID/bundle.tar.zst` and every other path under the state root stay refused ("use retained/ID/overlay"). A layer retained over a directory base records `weak`, which R1b refuses as a lower; TAR (sealed as `strong`, `overlay_seal.rs:443-451`) and Git (`git-tree`) layers branch.
- **`over`**: the IDs whose `retained/<ID>/overlay` a `new` named as a lower, kept in the attempt's state before its spawn and copied into the `retained.jsonl` line.
- **`--max-retained N`** (default 4096, `0..=16384`; 0 refuses `retain`): a `new` with `retain` needs `preserved + retained + live retain attempts + count ≤ N`, else `capacity`. Retained entries never count toward `--max-attempts` (Keystone #1).
- **Reserved IDs:** the redraw check (`daemon.rs:816`) also refuses retained and preserved IDs; the reviewed `tempdir_in` statement (`IR-B0112-M01`) is untouched.
- **Restart in R1c-1** (recovery is R1c-2). `Supervisor::open`, after `RequestLog::open` (`:387`): `private_dir(retained/)`, `RetainedLog::open` (the engine's checked open, syncs and replay), then the preserved IDs (live record IDs and valid names under `retained/`), then `reconcile`, which never enters `retained/`, then `resolve_interrupted`. Preserved entries stay on disk untouched, keep their IDs reserved, count toward `--max-retained`, and are not served: `list` omits them, `finalize`, `diff`, `stats` and use as a lower answer `invalid_request` ("attempt ID was retained before the daemon restarted; this release does not serve it again"), `destroy` answers `retained`. A record whose rename never happened stays live until R1c-2's recovery aborts it; it only reserves its ID and one slot.
- **Identity (ruling 3).** Each record holds the attempt ID, the base, the paths, `layer_digest`, `sealed_at`, the prefix (the child's records: each lower's path, `layer_digest` and `sealed_at`; a bundle position names its cache path) and `over`. No R1c-1 code looks a layer up by digest: the retained-lower exception and `over` resolve a requested path to an ID. R1b's stack check still compares digests to judge a stack (R1b §5.3); that is a consistency check over requested lowers, not provenance.

### 5.8 Removal of sealed trees, and the commit rename

`overlay_pack::remove_tree(path)`: `open_root`, the existing `remove_contents`, then `remove_dir` of the root, whose error reports anything left. It replaces `fs::remove_dir_all` in `reconcile`'s two loops and in `destroy`; a disk attempt is one `remove_tree` of its root (with `overlay/` inside), a RAM `overlay_dir` its own. So a crash between seal and rename cannot block the next start (Keystone #2), and a finalized tmpfs attempt can be destroyed. Mount handling is unchanged: `cleanup` still unmounts `mnt` and below first, and `remove_dir_all` also descended into a mounted directory.

`overlay_pack::rename_no_replace` takes `(old_dir: impl AsFd, from, new_dir: impl AsFd, to)` instead of one `&OwnedFd` (`overlay_pack.rs:1071`; sweep 3 Claude N7); its caller `unlink_if_same_named` (`:1125`) passes its directory twice, and the commit passes `rustix::fs::CWD` with absolute UTF-8 paths. A cross-filesystem `retained/` fails with `EXDEV` at R3 (`aborted`, `io`); there is no start-time device check. A state filesystem without `RENAME_NOREPLACE` (OpenZFS before 2.2, for one) fails R3 with `EINVAL` on every retain, only after the finalize work; the docs name the supported filesystems (ext4, xfs, btrfs, tmpfs) and the message says the filesystem lacks no-replace renames (sweep 5 Claude N4). A start-time probe is not taken: it would have to create a scratch entry and rename it to a free name, a new creation site for a check the documented limit already covers (§9.5).

### 5.9 Lock order (re-verified on `cf8f626`)

1. **`daemon.lock`**, held for the daemon's life (`daemon.rs:336`, `:400`): serializes every request, both logs, and every change under `attempts/` and `retained/`.
2. **Finalize:** fsck's own transaction commits first (`overlay_fsck.rs:208`); then the top's **overlay root flock** (`SealOperation::acquire_until`), then seal's **`BEGIN IMMEDIATE`** (`overlay_seal.rs:456`), released when `SealOperation::seal` returns (`:358-364`) or `finish_if_sealed` reports an earlier seal. **No archive lock:** "Seal never acquires an archive lock" (`overlay_seal.rs:276`); `docs/sandbox.md:613-616`. The archive flock belongs to commit, which takes the overlay lock first (`write_overlay.rs:7350-7363`; `docs/sandbox.md:608-609`) and which workers never reach (`--no-recreate-index` refuses overlay commits, `docs/sandbox.md:2238-2245`).
3. **S (every finalize):** one layer root flock at a time (exclusive, bounded), only after the seal returned, never while holding the top's; no database transaction; no archive lock.
4. **Child:** `publish_layer` holds its stage root's flock across rename and restore; a hit holds a destination's flock shared until it returns the path, exclusive only while it finishes an unfinished restore. The child opens its lowers before its top (`main.rs:2492-2521`), so it holds no other overlay root flock then.
5. **Nesting (sweep 2 Claude N4):** from step 2b `sandbox run` composes `args.lower` under its top's root flock (§5.3), so a bundle lower's hit takes that entry's flock inside the top's; `overlay seal DIR --lower BUNDLE` composes under its top's flock the same way (`overlay_cmd.rs:544-567`), so with the hit's lock it nests identically. Every nesting is the top's root flock first, then a cache entry's, and nothing takes a top's root flock while holding an entry's. It cannot cycle: `publish_layer` holds only its stage's flock and never a top's, and S takes entry flocks while holding no top's flock. T20.3 covers the wait.

## 8. Risks

1. **R1c-1 alone is not the whole feature.** A restart keeps retained trees and their IDs but does not serve them, and nothing can be forgotten through the API until R1c-2; a cut-off retaining finalize resolves to `interrupted` even when its tree survived. Recommendation: no release tag between R1c-1 and R1c-2 (Keystone decides).
2. **Sync cost.** Every finalize, retained or not, fsyncs every file of the top and of every lower, cache entries included, and their ancestors, each time (ruling 1+2 as written); XFS issues a device flush per `fsync` even for a clean file when the log shares the data device, so a lower with 10,000 files costs about 10,000 flushes per finalize, and a 100,000-file prepared layer can hold the serial daemon, and every other client, for minutes (sweep 2 Claude N9). The PR times it (§7). Ruling 1+2 fixes what is synced, not which thread does it: running S on a worker thread while the attempt stays `finalizing` is an option for Keystone; skipping already-synced entries is ruled out.
3. **Durability rests on the kernel and on the user's storage.** An error a previous fsync (another process's, or a run before a restart) already consumed, or one lost when an inode with failed writeback was evicted, is not reported to a fresh descriptor; poisoning covers only errors this daemon saw in this run. The base is not a layer and is not synced (§1.1): the user keeps it durable, and since the gates compare metadata only, a lost base write whose metadata survived need not be refused. A retained attempt survives a reboot only if the state directory, the bundle cache and every lower are on persistent filesystems; `$XDG_RUNTIME_DIR`, which the docs suggest for short socket paths (`docs/sandbox.md:2482-2484`), and often `/tmp` are tmpfs (sweep 2 Codex N3). Documented.
4. **Finalize hashes a TAR base in the serve loop.** Worker tops record `pending` and no writable index, so seal hashes the whole archive uncached under the top's root flock (digest caching is cut); Git bases do not hash. Timed in the PR.
5. **`Detaching`** is what a finalize gets while a container still runs: `docker run -v` gives the container its own copy of the mount, so the daemon's own unmount removes the host mount and the child keeps serving the container (sweep 1 Claude N3). The attempt's host path is then gone for the harness; the container's later writes still reach the overlay through the child and are sealed by the retry after the container stops; `destroy` is the other way out. This departs from "leave the attempt mounted" (source `:114`) because a non-lazy unmount that succeeds cannot be undone; the docs say to finalize only after the container stopped.
6. **Older fillers** (a ratarmount older than R1c-1 using the same cache) publish without the entry lock; a hit then waits for nothing, but its publication check still finishes or refuses a root left writable, so the only exposure is a hit racing an old filler's restore, which ends with the same sealed mode either way.
7. **Shared cache contention.** A hit holds the entry lock shared through its verification, and S holds it exclusively through its fsyncs. A finalize (S) whose cache entry is being verified by a hit of another daemon or CLI mount waits up to `FINALIZE_WAIT` and then answers `in_use`; a child whose hit waits behind another daemon's S can reach the batch `--timeout`. Both are retryable; documented with the cache notes.
8. **The engine extraction touches R1a's landed code.** It changes no rule or byte, R1a's tests run unchanged, and `policy.py` re-reviews the moved sites in the same commit.
9. **Downgrade.** An R1a or R1b daemon refuses a `requests.jsonl` with `op: "finalize"` lines (fail closed) and cannot remove a sealed tree in `attempts/`; documented order in §5.12.
10. **Departures from the source doc**, each for a ruling, a Keystone point, the scope rule or a code fact: retained attempts do not count toward `--max-attempts` (Keystone #1); retained state is `retained.jsonl` and the directory, not `state.json`; `--max-retained` is capped at 16,384; the child-exit wait is `FINALIZE_WAIT`, not the whole `--timeout`; `retain` is refused with `tmpfs` and on bases outside §5.5; a gate refusal is `io`; `erofs_denied` may be `null`; branching through the supervisor works over TAR and Git bases only; every finalize, not only a retained one, pays the sync (ruling 1+2).
