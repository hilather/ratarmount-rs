## 1. Goal

1. **Restart recovery.** After a supervisor restart, each attempt retained before it is matched with its `retained.jsonl` record, its base registration and its index folder, its commit rename is made durable, and it is served again (`list {all: true}`, `diff`, `stats`, finalize's fast path, use as a lower). A finalize cut off by the restart answers its stored report only for an entry recovery served in that same start, and only after R1c-1's fast path, S included, succeeds for it. Nothing in `retained/` is deleted by recovery; an entry that does not match is listed `retained_damaged` with its reason (Keystone fix (4)) and advice that depends on why, and is not served until a later start finds it matching.
2. **A target answered `not_found` never later resolves to `done`** (Keystone note 2). `not_found` is answered only for a target positively known to be gone: no live record of its instance and no tree that could be its layer, or forgotten. That holds for every retry of a stored target once R1c-2 lands, R1c-1's in-run orphan record included. A database busy at start is temporary: every request naming that entry, a retry of a stored target included, answers `in_use` with the restart advice, appends nothing and stays retryable.
3. **`forget {id}`** (protocol version 2) removes one retained entry (served, damaged, unacknowledged, or a record whose commit never happened), crash-safely, and ends its retry-window pins (approval note (a)). It refuses while anything that could still be mounted depends on the entry by recorded identity, and on every ambiguous reference, with an error naming what blocks. Forgetting what each refusal names, then retrying, always ends on every state the supervisor can produce, also after records, databases or trees are lost. Every `io` answer of `forget` and of `reconcile` names the path its failing call acted on, and for a removal the first entry that could not be removed (Keystone fix (7)).
4. **Partial fsck progress.** A finalize's reported `fsck_result` keeps every repair an earlier try made, also when that try's fsck failed after removing host content.
5. **`--normalize strict`.** Tests show finalize's `patch_hash.patch` equal to `ratarmount diff --hash --json --normalize strict` and different from the `exact` default (the blocked R1 plan's old blocker 5), and the docs say how to reproduce it.
6. **R5 docs.** The journal is not model context; the hidden-tests recipe adds the tests layer only in a direct grading mount, never through the supervisor. That mount repeats the worker's view (`uid`, `gid`, `umask=022`, `allow_other`, `noatime`, `--no-recreate-index`, `--no-file-versions` and the index folder). The recipe's grading function builds it without a shell and mounts nothing unless it read the attempt's lower stack completely; a FUSE test runs that function and compares the two views file by file (Keystone fix (1)).

**Boundaries stated for Keystone's attention** (as R1c-1 §1.1 states its own):
- **An entry with nothing readable refuses nothing.** An unrecorded tree whose database cannot be read holds no reference, so there is nothing to confirm or call ambiguous; every reference that does exist refuses when it is ambiguous (§5.3 rule 3). Reading "unknown" as "may depend on anything" would make such an entry refuse every other `forget` while every entry that names it refuses its own `forget`, a deadlock that one deleted database file reaches after `retained.jsonl` was moved aside. Such an entry is never served, and it is itself held by every entry that names it (sweep 1, Claude N4). An unrecorded entry whose database was only locked at start is not "nothing readable": its references are unknown until a restart reads them, so meanwhile every `forget` of another entry answers `in_use` with the restart advice (§5.3 rule 4; sweep 2, Claude N10), as every request naming that entry does (§5.1). A recorded entry's references come from its record, so its busy database changes nothing here.
- **Circular references made by an outside edit** have no order through the API. R1b and R1c-1 never make one, and losing records, databases or trees never makes one (§5.3). A tree inside `retained/` replaced by hand with a layer that names other retained entries, or prefix rows written by hand, can: `forget` then refuses every member, naming the others, and the docs give the manual repair (sweep 1, Codex B2).
- **Only something that could still be mounted is a dependant.** A record whose tree is not in `retained/` (an orphan record, a damaged record whose tree is gone, a `forgetting` entry once its rename back is durable) still records references, and `forget` ignores them (§5.3). Nothing could compose such a record, so its references protect nothing. Counting them would also keep a hand-removed tree's record refusing forever, which undoes the manual repair above, and would turn recovery's one-pass decision into a fixed point (§5.2). A `forgetting` entry whose rename back is not known to be durable (its F2 failed, or ran on a poisoned device) keeps its references, since a power loss can still put its tree back in `retained/` (sweep 2, Claude N5; sweep 3, Codex B1). T9 (g) and T7 test who counts.
- **One R1c-1 answer changes when R1c-2 lands** (note 2; run 2 sweep 1, Claude B1). R1c-1 answers `not_found` to a retry whose retain never renamed anything, whose `aborted` append failed too and whose attempt was then destroyed: its record is live, and its layer is gone (R1c-1 §5.4 step 1, its run 2 sweep 4 Codex B3, its T22). Note 2 allows `not_found` only without a live record, so R1c-2 answers that retry with the not-served `invalid_request` ("its commit did not complete") until the record ends, by a restart that aborts it (§5.2 row 4) or by `forget`; then `not_found`. The answer only ever moves from not-served to `not_found`, never back, and no outside copy of the destroyed layer placed at `retained/ID` can turn an earlier `not_found` into `done`. Step 2 rewrites R1c-1's T22 and the R1c-1 docs row that promised `not_found` there (§6, §5.8).

## 3. Out of scope

- **R1c-1 redesign.** R1c-2 uses only the seams R1c-1 names (§5.13 there) and the additive ones of §5.9. A reviewer request to change R1c-1's design (its record format, its syncs, its fast path, its stop, its statuses, its platform rule, its step-1 answers other than the one note 2 narrows, §1.1) is recorded here, not planned.
- **Coverage outside the sandbox supervisor path,** and **non-Linux sandbox support**: `forget`, like finalize and `retain`, answers `invalid_request` on other platforms before anything is looked up (R1c-1 §5.5's rule), and the daemon does not start there (`serve` answers `unsupported`, `daemon.rs:1285-1291`).
- **R2–R4** and the source doc's §9.
- **Request IDs on `forget`** (source doc `:97`; R1c-1 §3). A lost `forget` answer is retried by name; `not_found` then means already forgotten (Risk 4).
- **Re-adopting unrecorded trees.** A tree in `retained/` without a live record (the log was moved aside or lost) has no instance and no report; it is listed `retained_damaged` and can only be forgotten, or served again by restoring `retained.jsonl` with the daemon stopped.
- **Re-checking a damaged entry within a run,** a busy one included: only the next start's R2 re-reads it (Keystone note 2 rejects serving on a match without that re-read; Risk 15).
- **A base identity comparison at R2** beyond the registration and `indexes/<base>/` checks Keystone named: a base re-registered under the same name with another source passes R2 (Risk 14).
- **Running S at recovery for every entry** (§5.2), **persisting poison marks** across restarts (R1c-1 Risk 3), and **repairing** damaged entries.
- **Moving the state directory.** Records hold absolute paths; an entry recorded under another state root is damaged, with the advice to start the daemon at that root (§5.2).
- **Resolving circular references made by outside edits** inside the API (§1.1, boundary 2): manual repair, documented.
- **Protecting a retained layer from a direct mount** that uses it as a `--lower` (a grading mount), or from an attempt of another supervisor: such a mount holds no lock `forget` can see; the docs say to unmount grading mounts before `forget` (Risk 5).
- **Deleting content an outside actor made undeletable** inside a retained tree, such as a directory the daemon cannot open: `remove_tree` removes everything else and names the first entry it could not remove, in `forget` and, after a crash, in `reconcile`, exactly as for any attempt (Risk 12).
- **`reconcile`'s start refusals that are not `io`** (a name that is not UTF-8 or not valid, an unsafe stale mountpoint) keep their text; F0 keeps `forget` from producing the last one (row 20).
- **CI wiring** for the FUSE and Python tests: hand-run and recorded in the PR, as for R1a, R1b and R1c-1.
- **Identity matching of prefix rows that name no retained path** (§9).

## 5. Design

### 5.1 Protocol

- **v2 `forget {id}`**, `deny_unknown_fields` through the enum, no `request_id` (an unknown field there, as on every v2 operation but `new` and R1c-1's `finalize`). No v1 form: v1 `forget` stays an unknown operation (`invalid_request`, R1a U1). Answer: `{"forgotten": true}`.
- **Order of checks:** the platform rule first (R1c-1 §5.5), then `validate_name(id)`, then the lookup and refusals of §5.4. Each refusal changes nothing.
- **Statuses** in `list {all: true}` (R1c-1 §5.1, §5.7; attempts, then retained entries in ID order, each in the v1 attempt shape): `retained` (also every recovered entry), `retained_damaged` (new in step 2), `forgetting` (new in step 3: a `forget` that failed after its first step; a retry resumes it). R1c-1's unacknowledged entries keep R1c-1's `finalizing`. v1 `list` and v2 `list` without `all` are unchanged, so R1a's U2 equality holds.
- **The listing's `reason`** (Keystone fix (4); run 2 sweep 1, Codex B1). A `retained_damaged` or `forgetting` item of `list {all: true}` carries one more member, `reason`: the reason and advice its not-served answer gives (below), without that answer's opening. No other item has it, so v1 `list`, v2 `list` without `all` and every attempt or served entry keep their bytes. The member is additive, as version 2 grows (row 14); R1c-1's Python client ignores unknown keys (row 16), and R1c-2's gives it as `Attempt.reason` (§5.8).
- **Answers for entries that are not served** (D8, D15; Keystone note 2). R1c-1's not-served answers take R1c-2's reasons. A retry whose stored target is in neither the attempts map nor the retained map is answered by R1c-2's lookup, which takes the place of R1c-1's kept-target re-read (`kept_unserved`, §4.1 H) and reads no database. Its order:
  1. a live record of the stored ID with another instance: the ID's one record is another attempt's, so the target is gone, and the retry gets R1c-1's `not_found`, whatever that entry's state;
  2. a live record of the stored instance: a `retained_damaged` entry, a `forgetting` one, or R1c-1's in-run orphan (a retain whose rename never happened, §1.1), answered by the table;
  3. no live record, but a `retained_damaged` (unrecorded) or `forgetting` entry of that ID, whose tree may be the target's layer with its record lost: the table;
  4. otherwise, no live record and no tree: `not_found`.

| Entry | `finalize` (no stored target), `diff`, `stats`, use as a lower | A retry whose stored target is the entry |
| --- | --- | --- |
| `retained_damaged`, its database busy at start | `in_use`, with the restart advice | the same `in_use`; nothing is appended and the record stays `retryable` |
| `retained_damaged` for any other reason | the not-served `invalid_request`, with the reason and its advice | the same; nothing appended; stays `retryable` |
| `forgetting` | the not-served `invalid_request`: "it is being forgotten; retry forget", plus "after checking the storage, restart the daemon to finish it" when its device is poisoned (§5.4) | the same, until F4 |
| R1c-1's in-run orphan (its attempt destroyed; not listed, as in R1c-1) | the not-served `invalid_request`, "its commit did not complete, so nothing was retained" | the same, until a restart aborts the record (row 4) or it is forgotten; R1c-1 answered `not_found` (§1.1) |
| forgotten, or no live record and no tree | `not_found` | `not_found` |

  Every not-served message keeps R1c-1's opening, "attempt ID has a retained record that this daemon does not serve:" (`r1c1-impl retained.rs:402-411`), and goes on with the reason and its advice; the busy one reads "…does not serve: its database was busy when the daemon started (another process held a lock on it); stop that process, restart the daemon, then retry". `destroy {id}` of any of them stays R1c-1's `retained`. No request re-reads a damaged entry's database or serves it within the run, and no answer for a damaged entry says its result is kept: only the next start's R2 re-reads it, and only R2 can serve it. So `not_found` is answered exactly when note 2 allows it, for a target with no live record of its instance and no tree that could be its layer, or forgotten; no later start can serve such a target, so it never resolves to `done`. An answer moves from not-served to `not_found` (a record ended, a tree removed), never the reverse, with one exception that still never reaches `done`: moving `retained.jsonl` aside turns another instance's tree into an unrecorded one, which answers not-served (§5.8 says so). Code and reason come from R2 (§5.2): busy is `OverlayError::is_locked()` on `read_no_recovery`'s error, as fsck maps it (`overlay_fsck.rs:149-158`), with `busy_timeout(0)` (`overlay_meta.rs:333`).

  R1c-1 leaves a request ID free for exactly two refusals before `begin`, `not_found` for an `id` that names nothing and the not-served `invalid_request`, because no attempt was targeted (R1c-1 §5.4 step 1; `r1c1-impl docs/sandbox.md:2836-2841`). The not-served refusal now has two codes, `invalid_request` and `in_use`, and both leave the request ID free (T11); the docs say so (§5.8).
- **Reasons and advice** (sweep 1, Claude N6). Step 2's messages end before their `forget` clause ("or forget it", "forget it…"), and step 3 adds it with `forget`, so no `forget` text lands before step 3 (Keystone fix (2); run 2 sweep 1, Claude N2); T1 and T6 assert the reasons, T8 the clause:
  - busy at start: `in_use`, restart (above). A recorded entry's references come from its record, so a busy database blocks no other `forget`; an unrecorded one's references are unknown until the restart (§5.3 rule 4);
  - recorded under another root: "it was recorded under ROOT; start the daemon with `--state-dir ROOT`";
  - its state directory is on TYPE: "the state directory is on TYPE, where retained attempts are not served; move the state directory to ext4, xfs, btrfs or tmpfs, or forget it";
  - its base B is not registered, or `indexes/B/` is missing (Keystone fix (4)): "register base B again with its original source and options, or restore `bases.json` and `indexes/` with the daemon stopped; then restart the daemon, or forget it";
  - no record: "it has no record in retained.jsonl; restore retained.jsonl with the daemon stopped, or forget it";
  - its database cannot be read for another reason: "check the storage and restart the daemon, or forget it";
  - R1c-1's in-run orphan: "its commit did not complete, so nothing was retained; forget it to release its ID";
  - every other reason (a deleted or unsealed database, another layer, a prefix that differs from the record, a symlink, a tree gone, a stray directory): "forget it".
- **No new error code.** `forget` refuses with `in_use` (a dependant, an unconfirmed reference, an unrecorded entry busy at start, a mount, the layer's lock held), `invalid_request` (an attempt in the attempts map; another platform), `not_found`, `unsafe_path` (F0: the tree's root no longer passes R0's check, whose existing code it is, `daemon.rs:66-75`), `io`. Every `io` answer of `forget`, of recovery and of `reconcile` names its step and the path its failing call acted on, through R1c-1's `io_error` (approval note (1); Keystone fix (7); §4.1 B), for example "forget F3: removing PATH/overlay/x/y: Permission denied".

### 5.2 Restart recovery

**Where.** In `Supervisor::open`, R1c-1's order is: lock, `attempts/`, `indexes/`, bases, RAM root, `RequestLog::open`, `private_dir(retained/)`, `RetainedLog::open`, the names under `retained/` without a live record, `reconcile`, the pins of every retained target (`set_pins`, §4.1 A), `resolve_interrupted` (R1c-1 §5.7; `r1c1-impl daemon.rs:455-504`). Recovery adds R0–R2 and R4 after the name scan, and R3 after `set_pins` and before `resolve_interrupted` (R1c-1 §5.13). R1c-1 computes the pins from the live records and bare names, so a record recovery aborts is not pinned, and its finalize records become evictable; served and damaged entries stay pinned, and so does R3's `done` record (sweep 2, Claude B1). Off Linux recovery does nothing beyond R1c-1's preservation (no retained state can be made there). A refusal before `reconcile` deletes nothing under `attempts/` or `retained/`; every append goes through R1c-1's engine (§5.6).

- **R0. Entries.** Every name under `retained/` must be UTF-8, pass `validate_name` and pass `private_dir`'s checks (a directory, not a symlink, owned, mode without group or other bits), as `reconcile` requires of `attempts/` (`daemon.rs:454-461`). A name that is not UTF-8 never reaches R0: R1c-1's name scan refuses it first, naming `retained/` (§4.1 D). `private_dir` first creates a missing directory (`daemon.rs:52-64`), so R0, F0 and `reconcile` run only its checks (`:66-75`), as one function whose `lstat` error names the path, on an entry already listed, and create nothing (sweep 3, Claude N5). Otherwise the start is refused, naming the entry and the remedy, before any recovery append and before anything under `attempts/` or `retained/` is deleted. The remedy is `chmod 700` for a directory whose mode is its only failure, else to remove or rename it with the daemon stopped, as for a bad `attempts/` entry today (sweep 3, Claude N4). The logs' own open-time maintenance (a torn tail truncated, compaction leftovers removed, row 21) has run by then, as it does today (sweep 2, Codex N5). R1c-1 refuses only a non-UTF-8 name there (§4.1 D), so the other checks are a start-time refusal for an R1c-1 state with such an entry (CHANGELOG).
- **R1. Complete durability** (the blocked R1 plan's old blocker 3, restart half: "complete the relevant directory durability operations during recovery before acknowledging retained finalizes or accepting log appends"). Only when `retained.jsonl` has a live record or `retained/` has an entry; with no retained state recovery makes no system call, so a v1-only state starts exactly as today. First R1c-1's filesystem-type probe on `retained/` and `attempts/` (D12):
  - **off R1c-1's allowlist** (a state directory copied or restored onto overlayfs, NFS or FUSE): recovery acknowledges nothing. It makes no sync, lists every entry with a tree in `retained/` as `retained_damaged` with that reason (§5.1), and R4 serves nothing, so R3 finds no target and every cut-off finalize is left to `resolve_interrupted`. R2's rows 3 and 4 still append `aborted`, since ending a record acknowledges nothing (sweep 3, Claude N6). The daemon starts, and `forget` still works, since its syncs use the discard sync, which applies no allowlist (§5.4, D2). Refusing the start instead would leave no way to run `forget` (sweep 1, Claude N7);
  - **on the allowlist:** R1c-1's `sync_dir_strict` of `retained/`, then of `attempts/` (the poisoned set is empty at start). A failure refuses the start with `io_error` naming the step, the directory and the error, as R1a's open does (row 2).
- **R2. Match records with trees.** "The record's layer" means that each of these checks passes, in this order; the first that fails is the entry's reason (§5.1):
  1. the record's `paths.overlay` is `<S>/retained/ID/overlay`, where `S` is the canonical state root;
  2. `retained/ID/overlay` is a directory, not a symlink (`symlink_metadata`, before any open);
  3. read with `read_no_recovery`, it is sealed with the record's `layer_digest` and `sealed_at`: R1c-1 §5.4 step 1's kept-target test. A locked database is "busy at start"; another read error is "cannot be read"; no database, an unsealed one and another identity each have their own reason;
  4. `lower_layers()` parses and equals the record's `prefix` (paths, digests and `sealed_at`, in order; both come from the same child records);
  5. the record's `base` is registered in the `bases.json` the start loaded (`daemon.rs:352-373`; Keystone fix (4));
  6. `indexes/<base>/` is a directory, not a symlink (`create_base` made it, `daemon.rs:565`; Keystone fix (4)).

  Checks 5 and 6 catch a base removed by hand with the daemon stopped (row 23): without them the entry would be served, and `diff` and the fast path would answer "unknown base" (`daemon.rs:777-780`; `r1c1-impl retained.rs:887`), or a cut-off finalize would fail only inside R3's fast path. A base registered again under the same name passes both (Risk 14). An unrecorded tree has no record and no base: recovery runs check 2 on it and reads its identity and prefix from its database (check 3's read, a lock there included), for §5.3.

| Live record | `retained/ID` | `attempts/ID` | Result |
| --- | --- | --- | --- |
| yes | the record's layer | (any) | `retained`: served and acknowledged (R4). A leftover `attempts/ID` is deleted by `reconcile` like every attempt. |
| yes | present, not the record's layer | (any) | `retained_damaged`, with the first failing check as its reason. Never deleted or changed. |
| yes | absent | present | The commit never happened (a crash before R1c-1's R3, an R3 failure whose `aborted` append also failed) or a `forget` renamed it back (§5.4): append `aborted`; `reconcile` deletes `attempts/ID`. |
| yes | absent | absent | The commit never happened and its attempt was then destroyed (R1c-1's orphan record, R1c-1 §5.6), or an outside actor removed the tree: append `aborted`. |
| no | present | (any) | `retained_damaged` (unrecorded), base `""`. Its identity and prefix are read back from its database when readable (§5.3). |

  The two `aborted` rows have one exception: a record that a dependant with a tree in `retained/` still references (§5.3, confirmed or ambiguous) is kept as `retained_damaged` without a tree, so its ID stays reserved and its slot held until `forget`. Entries without a tree in `retained/` reference nothing (§5.3), so the rows are decided in one pass with no fixed point: an entry renamed back by a cut-off `forget` or aborted in this same recovery never keeps another (sweep 1, Claude N5; T7 tests the first, Keystone fix (2)). Only an outside actor makes the exception: R1c-1 admits a retained lower only after its commit (row 4), and `forget` refuses a referenced entry before it moves anything. The two `aborted` rows are what R1c-1 §5.6 promises for a live record whose tree is not in `retained/` ("until R1c-2's recovery aborts it"). Order: every identity and prefix is read first (from the records, and from the databases of unrecorded trees), so a referrer that is itself unrecorded is seen; then every row is decided; then the `aborted` lines are appended (one synced append each; a failure refuses the start, as `resolve_interrupted` does, `requests.rs:842-847`); then the retained log's health is checked (Log health below); only then does `reconcile` delete anything.
- **R4. Serve.** Each served entry enters R1c-1's retained map as exactly the `RetainedEntry` R1c-1's commit makes (§4.1 O; D3): `attempt` `{id, base, path: <S>/retained/ID/mnt, overlay_dir: <S>/retained/ID/overlay, status: "retained"}`, the record's `instance` and `report`, `records` (the record's `prefix` as `LowerLayerRecord`s) and `acknowledged: true` (its rename is durable after R1). No `attempt_state` is made, as R1c-1's commit removes it (run 2 sweep 1, Claude N4); `over`, `layer_digest` and `sealed_at` stay in the live record, where §5.3 reads them. R1c-1's rules then apply unchanged: `list {all: true}`; `diff` (classified and gated) and `stats`; the fast path; use as `<S>/retained/ID/overlay`; `destroy` → `retained`; `held` and `--max-retained`. Damaged entries go into a separate `damaged` map (ID → base or `""`, reason, whether its live record exists and with which instance, and the identity and prefix of §5.3 where known), so R1c-1's retained map and its code paths keep their meaning. Their IDs are in `held` through their live record or their bare name, so R1c-1's not-served answers apply, with §5.1's codes, messages and listing `reason`.
- **R3. Resolve cut-off finalizes** (source `:129`), after `reconcile` and before `resolve_interrupted`. For the replayed `running` finalize record, if any (R1c-1 §5.2: `v: 2`, `target {id, instance}`; D5), when R4 put `target.id` with `target.instance` into the retained map in this start and the stored report satisfies the request: "satisfied" means the record's `op_hash` equals `op_hash({"op":"finalize","id":ID})` (no `pack`), or equals it with `"pack":true` and the report names a bundle. Then R3 runs **R1c-1's fast path for that target** (sweep 1, Claude B1 and Codex B1): `finalize_retained` (§4.1 I), which re-reads its recorded lowers, runs the durability preflight and S over `retained/ID`, `indexes/<base>/` and every lower its records name, with R1c-1's entry locks, poisoning and messages (R1c-1 §5.4 step 1, §5.5, §5.6). It does not re-read the entry's own database, whose identity R2 read in this same start: the one re-read note 2 allows skipping. Only if all of it succeeds does R3 write the `done` line through R1c-1's `finish_finalize`, with `result` equal to the record's `report` byte for byte and `attempts: [target.id]` (so the ID stays reserved, R1c-1 §5.2). A failure of that append refuses the start, as a failed append of `resolve_interrupted` does (`requests.rs:842-847`; sweep 2, Claude N9), and so does a compaction that the append leaves `Broken` (Log health below). Any other failure leaves the record to `resolve_interrupted`, which writes R1c-1's `v: 2` `failed interrupted`: a purged cache entry (R1b's re-read), a preflight refusal, an S error, an entry-lock deadline. An fsync error poisons as in R1c-1, and the entry itself stays served.
  - **Only what R2 served** (Keystone note 2). A target that R2 found busy, damaged for any other reason, or gone (aborted, or no record and no tree) is never resolved to `done` in this start. R3 never reads an entry's own database, so a lock released after R2's read changes nothing: that record, too, is left to `resolve_interrupted`. R1a replays that stored `interrupted` unchanged, and a new finalize after a restart that serves the entry answers its report.
  - The record may be the original retaining request (killed after R1c-1's R3 or R4) or a later finalize of the retained entry killed inside its own fast path. The two have the same target and may have the same body, so they are treated alike; for the first, S runs a second time, which is harmless. A record an R1c-1 restart already resolved to `failed interrupted` stays so: R1a replays a stored answer unchanged, and R1c-1 §5.13 forbids rewriting it (R1c-1 Risk 1).
- **Log health** (sweep 3, Codex B2). A successful append can still leave its log `Broken`. Each `aborted` append and R3's `done` end with R1c-1's compaction check (§4.1 L: `r1c1-impl retained.rs:383`, `requests.rs:942`). A compaction that published its file but could not sync the directory sets `Broken` and reports nothing to the caller (`r1c1-impl state_log.rs:497-553`). A later append of the same start would fail, but none follows: no `aborted` comes after the last one; after R3's `done`, `resolve_interrupted` has nothing to write (at most one request is `running`, §4 row 3), and it never compacts (`r1c1-impl requests.rs:946-987`). So recovery checks `retained.jsonl` after its last `aborted` append, before `reconcile`, and `requests.jsonl` after R3's `done`. If either is `Broken`, the start is refused with `io`, naming the step and carrying the log's `unavailable()` text: the log, why it is `Broken`, and "restart the daemon" (`r1c1-impl state_log.rs:445-455`; D16). The restart is the remedy. The next open syncs the log and its directory before acting (row 2), and whichever file the name then holds, the old one or the compacted one, has the same live records. So the daemon never starts with a log that recovery left `Broken`.
- **R5.** `reconcile`, then `resolve_interrupted`, as R1c-1 has them, except that every `io` error of `reconcile` names the path its failing call acted on (Keystone fix (7); row 22), never only the attempt's root or a bare `io` error. `reconcile` names the paths of its own calls: the listing of `attempts/` or of the RAM root, an entry's check (R0's function above), and for a removal the first entry `remove_tree` could not remove (D17). The Mounter's `cleanup` errors already name theirs where they fail (D18: `/proc/self/mountinfo` for a mount-table read, the mount point for a wait on its mount process), so `reconcile` puts its step before the Mounter's message and adds no path of its own, which for a failed mount-table read would be the wrong one (run 2 sweep 1, Codex B3).

**Where S runs.** Recovery runs S exactly where R1c-1 would: before it answers a finalize (R3), for at most one target (row 3). It does not run S for every recovered entry, because serving an entry acknowledges nothing. R1c-1's commit ran S (its R1) before it appended the record (R2), and renamed (R3) only after that append was durable (R1c-1 §5.6), so for every live record only the two directory entries R3 changed can be unsynced, and recovery's R1 completes those. Any finalize of a recovered entry runs S again through R1c-1's fast path, which also covers a bundle cache entry purged and refilled while the daemon was down; only R1a's replay of a `done` record runs nothing. Running S for up to 4,096 entries at every start could cost minutes per lower (R1c-1 Risk 2).

**What recovery cannot see.** R1's syncs open new descriptors, as R1a's open-time syncs do. An fsync error that the previous run already consumed is not reported to them (R1c-1 Risk 3). That run poisoned the filesystem in memory and refused every finalize on it with "check the storage first" (R1c-1 §5.6); the restart docs repeat that a restart is the operator's statement that the storage was checked. On ext3, ext4, xfs and btrfs a failed metadata commit aborts the journal, so the restart's own syncs or appends fail and the start is refused; ext2, which R1c-1's allowlist admits by its shared magic number, has no journal (Risk 1).

### 5.3 Dependencies by recorded identity (Keystone's ruling)

**Identity and prefix.** Every retained entry E (served, damaged, unacknowledged, forgetting, or an orphan record) has an identity `I(E) = (layer_digest, sealed_at)` and a prefix `P(E)` (ordered rows `{path, layer_digest, sealed_at}`). Both come from its live record when it has one (R1c-1 records both, and the record is what dependants were built against), else from its database (`read_no_recovery`: sealed, `layer_digest`, `sealed_at`, `lower_layers()`), else they are unknown. `len(E)` is the number of rows of `P(E)`, and 0 when `P(E)` is unknown. Identities are kept in memory: read once by recovery, and taken from each new record at R1c-1's commit. `forget` reads no database.

**Dependants.** Only something that could still be mounted over X counts:
- a live attempt, through its `over`, which R1c-1 records before its spawn, unverified attempts included (R1c-1 §5.7);
- a retained entry with a directory at `retained/ID`, whatever its state (served, unacknowledged, damaged, unrecorded, or an orphan record of this run with a stray directory there), through its references;
- a `forgetting` entry until its F2 is trusted (§5.4), through the identity, prefix and `over` the `forgetting` map keeps (from its record, or from its database as recovery read it): its tree is in `attempts/`, but until the rename back is durable a power loss can put it back in `retained/`, served again with its live record or listed unrecorded (sweep 2, Claude N5; sweep 3, Codex N3).

A record without a tree in `retained/` (an orphan record, a damaged record whose tree is gone, a `forgetting` entry whose F2 is trusted) has no layer anything could compose, so it references nothing (sweep 1, Claude N5).

**References.**
- A row at position *j* of `P(E)` **names** X when its path is exactly `<S>/retained/<X>/overlay` with X a valid name: the path R1c-1's place rule admits and the child records (row 4). Every other row (a bundle position's cache directory, any user directory) names no retained entry.
- A recorded entry's `over` names each of its IDs too (attempt ID).
- A row naming X is **confirmed** when `I(X)` is known and equals the row's `(layer_digest, sealed_at)`, and `P(X)` has `j` rows whose `layer_digest`s equal those of `P(E)[0..j]`, in order. That is R1b's own stack rule (`lowers.rs:413-419`): neither the paths of those lower rows (R1b accepts a bundle and its source directory as the same lower) nor their `sealed_at` (R1b never compares it there) are compared, so no stack R1b admitted reads as ambiguous. An `over` ID X is confirmed when a confirmed row of `P(E)` names X.
- Anything else is **ambiguous**: X has no identity (no record and an unreadable database), or a different one (resealed, replaced, another layer at that path), or the record's `over` and prefix disagree.

No digest ever finds an entry: the ID or the path names the candidate, and digest, `sealed_at` and prefix only confirm it. A byte-identical copy at the named path confirms, and it is the same layer.

**`forget X` is refused** (`in_use`, nothing changed) iff:
1. a live attempt's `over` contains X: "attempt Y uses retained/X/overlay as a lower; destroy Y first";
2. a retained dependant E ≠ X has a confirmed reference to X: "retained entry E was built over X; forget E first";
3. a retained dependant E ≠ X has an ambiguous reference to X, whatever the prefix lengths: "retained entry E records retained/X/overlay as a lower, but X cannot be confirmed (REASON), so E may depend on X; forget E first";
4. an unrecorded entry U ≠ X whose database was locked at start (§5.1's "busy" reason), also while U is `forgetting` until its F2 is trusted (a recorded entry never triggers this rule, since its references come from its record): its references are unknown until a restart reads them, so "retained entry U's database was busy at start, so what it depends on is unknown; restart the daemon to read it" (sweep 2, Claude N10).

When E is `forgetting`, rules 2 and 3 end "finish forgetting E first" instead: a retried `forget E` resumes it, or after a poisoning the next start completes it (§5.4).

REASON says which check failed: X has no record and an unreadable database, X records another `layer_digest`, `sealed_at` or prefix, or E's record names X in `over` without a matching prefix row. Only the first adds "or restore retained.jsonl with the daemon stopped", the one case that restoring the log resolves. The answer names every blocking entry, cut to R1b's `MESSAGE_BYTES` (`lowers.rs:44`). The first draft's length condition on rule 3 is gone: the ruling makes an ambiguous reference unknown and requires refusal, and lengths read back from rows prove nothing about them (row 4; sweep 1, Codex B2).

**When forgetting everything works.** Every reference R1b admits points from a longer prefix to a strictly shorter one, confirmed or not: R1b refused a lower at position *i* unless it recorded exactly *i* rows (`lowers.rs:415`), so X, at position `j` of E's stack, has `len(X) = j < len(E)`. Each such reference is also confirmed when it is made: E's child recorded X with the digest and `sealed_at` R1b validated (`lowers.rs:473-477`), which are X's record, and X's rows have the digests of E's rows beneath it (`:415-419`). Losing a record, a database or a tree afterwards keeps the direction:
- a lost record moves where an identity is read, not the rows (the database holds the same child records);
- an unreadable database removes that entry's own references, and leaves references to it pointing from longer prefixes;
- a lost tree removes its entry as a dependant.

So on every state the supervisor makes, also after such losses, a remaining entry with the largest `len` is refused only by a live attempt, a mount, another process's lock or an entry busy at start (rule 4), all of which the operator can end (the last by a restart). On a poisoned filesystem `forget` also waits for a restart (§5.4). Forgetting whatever a refusal names, then retrying, therefore always ends. That is what the docs say; the API shows no prefix lengths (sweep 1, Claude N9). The blocked plan's digest read-back had no such guarantee (Codex sweep 6 #3, §10.1).

A cycle needs an outside edit: a tree inside `retained/` replaced, with its record lost, by a layer whose rows name other retained entries, or rows written by hand. `forget` then refuses every member, naming the others. The documented repair: with the daemon stopped, remove one of the named trees by hand (`chmod -R u+w`, then `rm -rf`), then start. Its record, if any, is kept as a damaged entry without a tree, which references nothing, so the others can be forgotten and then it (§5.2; T9 (e)).

**The three empty layers** (T9). A, B over `retained/A/overlay`, C over A and B, all three empty: one digest, prefixes `[]`, `[A]`, `[A, B]`. Each row names its entry by path and confirms by `sealed_at` and prefix, so the references are B→A, C→A and C→B, and the shared digest creates none. `forget` refuses A (naming B and C) and B (naming C), and C, B, A succeeds. With `retained.jsonl` moved aside, the same rows are read back from the databases, with the same result. If B and C were built over copies of A's and B's bundles instead, their rows name cache directories, no retained entry is referenced, and any order is correct: forgetting A and B removes nothing C's stack names.

### 5.4 `forget`

**Lookup**, after the platform rule and `validate_name`:
- an ID in the attempts map (also R1c-1's orphan record whose attempt is still live): `invalid_request` ("attempt ID is not retained; destroy it");
- an ID in R1c-1's retained map (served or unacknowledged), in `damaged`, a `forgetting` entry, or an orphan record of this run: forget it. An orphan record has its ID in `held` through a live record but is in no map; whatever sits at `retained/ID`, such as the stray directory that made R1c-1's R3 fail, is then not its layer and is removed with it;
- otherwise `not_found`, which after a completed `forget` means already forgotten.

**Refusals,** in this order, each changing nothing. The tree is `<S>/retained/ID`, or `<S>/attempts/ID` for a `forgetting` entry after F1.
1. §5.3's rules.
2. Any mount point at or below the tree, from R1c-1's `Mounter::mount_points()` (§4.1 N; its test overrides are D9's): `in_use` naming it. A failure to read the mount table is `io` with the Mounter's message, which names the file it read (`/proc/self/mountinfo`, D18); `forget` adds its step only.
3. When the tree's `overlay` is a directory, its root flock, `LOCK_EX | LOCK_NB` through `open_root` (the #240 lock, row 11), held on that descriptor until the tree is gone or the try stops (§5.6 lists it among the lock's holders). Another process holding it (an `overlay seal`, `unseal`, a commit, another daemon's S, a cache hit or fill) is `in_use`; the non-blocking lock keeps the serial daemon from waiting.

**Steps,** keyed on where the tree is; each is skipped when already done. After F1 the entry is `forgetting`, also after any later failure, and a retried `forget` resumes:
- **F0.** Tree at `retained/ID`: make it pass `reconcile`'s checks (row 20) before it can land in `attempts/`, so a crash after F1 never blocks the next start (sweep 2, Codex B1).
  - Its root must still pass R0's check (`private_dir`'s ownership, mode and type tests without its creation step, `daemon.rs:66-75`), else `unsafe_path` naming it, with nothing changed.
  - F0 opens the root once with `open_root` and keeps that descriptor for the rest of F0. A `mnt` inside it that exists and is not a directory is unlinked through it (`unlinkat`, which follows no symlink). Only an outside actor puts one there: R1c-1's trees keep their attempt's `mnt` directory. A mount on it was already refused above.
  - Then F0 fsyncs the tree's root on that same descriptor with the discard sync (D2), whether or not it unlinked anything, and F1 starts only once that sync is trusted (the poisoning rule below). An unlink changes `retained/ID` itself, which F2's syncs of `retained/` and `attempts/` do not cover (sweep 3, Codex B1). Syncing every time costs one directory fsync per `forget` and keeps nothing to remember between tries: a failed sync stops `forget` before F1 with `io`, and a retry runs F0 again from the start. The descriptor is `open_root`'s (`IR-B0046-M01`, `directory-handle-or-durability`), the one S syncs tree roots on, so F0 opens nothing through `open_dir`, whose reviewed reason does not name a tree's own root (§4.1 K, §5.10; Keystone fix (6)).
  - Content that `remove_tree` cannot delete, such as a directory the daemon cannot open, is no `reconcile` check; F3 meets it, as §3 and Risk 12 state.
- **F1.** Tree at `retained/ID`: `rename_no_replace(retained/ID → attempts/ID)` with absolute paths (R1c-1's two-directory form). Within a run no `attempts/ID` can exist beside a retained ID: `held` keeps the ID from being drawn, an orphan record's live attempt is refused by the lookup, and `destroy` removed its tree. So an existing one gets a defensive refusal: `EEXIST`, `io`, nothing moved, no `forgetting` entry, and a retry runs the whole `forget` again. On success the entry leaves the retained map or `damaged` for a `forgetting` map. That map keeps what §5.3 needs about the entry until F4: its ID and base, whether it has a live record and its instance, its identity, prefix and `over` (from the record; for an unrecorded entry the identity and prefix its database gave recovery), whether its database was busy at start, and whether F2 was trusted (sweep 3, Codex N3). `list {all: true}` shows it with the tree's current paths. It is not an attempt, so `destroy {base}`, `shutdown` and the final `destroy_all`, which iterate the attempts map (`daemon.rs:659-684`, `:1105-1114`), never touch it, and its ID stays in `held` until F4.
- **F2.** The discard sync (D2) of `retained/`, then of `attempts/`, each opened through the engine's `open_dir`. Its success counts only on a device that is not poisoned (the poisoning rule below); the `forgetting` map records whether F2 was trusted. Until it is, the entry stays a dependant through its references (§5.3).
- **F3.** `remove_tree(attempts/ID)` (R1c-1 §5.8). It removes everything it can; on a failure its `io` error names the first entry it could not remove (D17), the entry stays `forgetting`, and a retry runs F3 again.
- **F4.** For an entry with a live record, append `{"v":1,"id":ID,"t":"forgotten"}` to `retained.jsonl` (D7), then end its pin: `unpin` of its target, `(ID, instance)` (§4.1 A). For a bare name, remove it from R1c-1's set of names found at start (D4) and end its ID pin (D13). Either way the ID leaves `held`, and its finalize records become evictable under R1a's caps (approval note (a); sweep 2, Claude B1). They still reserve the ID while they live, as every stored answer does. From F4 on, a retry whose stored target is the entry answers `not_found` (§5.1): the entry is forgotten.
- With no tree (an orphan record, a damaged record without a tree, a resumed forget after F3) only F4 runs; with the tree already in `attempts/ID` (a `forgetting` entry), F2–F4.

**`io` errors** (Keystone fix (7)). Each names its step and the path its failing call acted on: F0 `retained/ID` (its open, `fstat` or fsync) or `retained/ID/mnt` (the unlink); F1 `retained/ID`, with `attempts/ID` named as the destination; F2 `retained/` or `attempts/`; F3 the first entry below `attempts/ID` it could not remove, for example a directory the daemon cannot open; F4 `retained.jsonl` (the engine's `failure` text names it, `r1c1-impl state_log.rs:204-206`); the root flock's open `retained/ID/overlay`; the mount table `/proc/self/mountinfo`, named by the Mounter where its read fails (D18).

**The record goes last, so every crash matches §5.2's table.**
- Before F1, at most F0 unlinked a non-directory `mnt` and synced the root, which no check of §5.2 reads; the entry is recovered as before.
- After F1 and before F4, a live record's tree is in `attempts/` (row 3: `aborted`, and `reconcile` deletes it); a bare name's tree is an ordinary leftover that `reconcile` deletes.
- After F3 and before F4, the record has no tree (row 4: `aborted`). Nothing references it: `forget` checked §5.3 first, and the serial daemon added nothing since.

So a cut-off `forget` completes at the next start, and its retry answers `not_found`. A trusted F2 makes the rename-back durable before anything is removed. If it were lost anyway, the next start finds the tree at `retained/ID` again: served again if F4's line was lost too (the forget simply did not happen), or an unrecorded damaged entry if it was not; `forget` clears either (sweep 1, Claude N12).

**Poisoning.** R1c-1 leaves an entry whose R4 met a poisoned filesystem for R1c-2's `forget` (R1c-1 §5.6). `forget` acknowledges a deletion, not data, but the deletion is safe only behind syncs:
- **Marks.** An fsync error in F0 or F2 is reported once, to that descriptor, and R1c-1's next R4 syncs the same directories on new descriptors and would get 0. So the discard sync marks the device poisoned on an fsync error, and it applies neither the poisoned set nor the allowlist before syncing (D2). An open or rename error poisons nothing. With that mark set, any later finalize on the filesystem is refused at R1c-1's durability preflight, before its stop (R1c-1 §5.5).
- **A sync on a poisoned device proves nothing**, which is why R1c-1 refuses S and R4 on one before their first fsync (R1c-1 §5.6; sweep 3, Claude N3 and Codex B1). So a sync of F0 or F2 is trusted only when it succeeded and the device is not in the poisoned set afterwards (poisoned earlier, or by that sync):
  - For a tree at `retained/ID`, a device already poisoned refuses `forget` before F0 changes anything, with `io` naming the earlier failure and the remedy (check the storage, restart the daemon, then retry `forget`). A root sync that fails stops it before F1 with `io`: after an fsync error, which poisons the device, with the same remedy; after any other error (the root's open or `fstat`, which poison nothing) a plain retry syncs again. Either way the tree stays at `retained/ID`, so it never reaches `reconcile` with a `mnt` whose removal no sync proves.
  - For F2, an untrusted sync stops `forget` after F2 with the same `io`. The entry stays `forgetting` in `attempts/`: a dependant whose retries get the not-served answer, and a retry stops there again while the device is poisoned. The next start, which clears the marks, completes it as it completes a crash after F1 (above).

  So on a poisoned filesystem `forget` waits for a restart, except for what needs no trusted sync: an entry with no tree runs only F4, whose `forgotten` line, if a power loss takes it, §5.2's row 4 replaces with `aborted`; and a `forgetting` entry past a trusted F2 finishes F3 and F4 in `attempts/`, which every start clears.

**What `forget` never does:** unmount, signal or stop anything; touch anything but its tree at `retained/ID` or `attempts/ID`; delete a bundle cache entry or a lower; open a database; wait for a lock.

### 5.5 Partial fsck progress

R1c-1's `FinalizeProgress` (R1c-1 §5.3; already kept per attempt across tries, with `packed`) gains `repaired: usize` (D6). Compositing's fsck gains a count of the repairs that cannot roll back (sweep 1, Codex B3):
- `overlay_fsck::fsck_counting(dir, repair, &mut resolved)` adds 1 to `resolved` each time its repair loop removes the host entry at a tombstone's own path. Each such removal resolves one `tombstone_content` finding, since the loop removes descendants first (row 12).
- `fsck(dir, repair)` calls it with a local counter and is otherwise unchanged for its other callers (row 12's list, `sandbox run` included).
- `check_connection` takes the counter too; seal's call (`overlay_seal.rs:463`) passes a throwaway, since seal never repairs.

Phase 1, `fsck_counting(top, repair = !sealed, …)`, adds to `progress.repaired`, per try:
- `report.repaired` when it returns `Ok`: its transaction committed (`overlay_fsck.rs:207-209`), clean or not;
- `resolved` when it returns `Err`: its SQL repairs rolled back, and the next try finds and counts them again, while its host removals stay done (`:362` runs before `:365-378` and `:208`).

A try whose fsck is not clean still fails the finalize, as in R1c-1, and its `errors:N` is never reported by a later try. The report's `fsck_result` is `repaired:K` when the total K is above 0, else this try's `result()`. K counts every repair that took effect, whichever try made it (sweep 1, Claude N13). A retry over a sealed top runs fsck read-only and adds 0. `sandbox run` passes a fresh progress and reports its single try, so its reports keep R1c-1's golden bytes (R1c-1 T1, T1b). A stored report of a finalized or retained attempt already carries its value; recovery serves it unchanged.

### 5.6 Durable logs and lock order

**One durable-log engine.** R1c-2 adds no log and no compaction code. `aborted` and `forgotten` lines go through R1c-1's `StateLog<RetainedRecords>`, and the finalize `done` resolutions through R1c-1's `RequestLog`, both the one engine R1c-1 extracted from R1a (R1c-1 §5.2). The logs keep their `sync_dir`. R1c-2's only new sync is the discard sync (D2), a supervisor function beside R1c-1's `sync_dir_strict` that fsyncs a directory descriptor it is given: in F0 the `open_root` descriptor F0 already holds, in F2 descriptors from the engine's `state_log::open_dir`. Recovery's R1 uses `sync_dir_strict`, and R3's S is R1c-1's own. `forgotten` follows `aborted`'s rules (exactly `v`, `id` and `t`; it ends a live record and is a no-op for another ID; compaction drops an ended record; §4.1 E). It is one line-schema addition, which an R1c-1 daemon refuses at start: fail closed, as R1c-1 §5.13 intends.

**Lock order** (`docs/sandbox.md:603-618`: overlay root flock, then the database transaction; the archive lock belongs to commit only):
1. `daemon.lock`, held for the daemon's life (`daemon.rs:332`, `:345`), serializes recovery, `forget` and every request.
2. Recovery takes no overlay root flock of its own, no write transaction on any overlay database and no archive lock. `read_no_recovery` takes SQLite's SHARED read locks only (`lowers.rs:5-9`); the log appends are file appends, not database transactions. R3's fast path takes R1c-1's entry locks, one lower at a time and never with a top's flock held (R1c-1 §5.9 item 3).
3. **`forget`** takes exactly one overlay root flock, its tree's `overlay` (`LOCK_EX | LOCK_NB` through `open_root`), after `daemon.lock` and before any change, and holds it on that one descriptor across F1's rename and F3's removal, until the tree is gone or the try stops. Under it: no database transaction (`forget` opens no database), no archive lock, no other root flock. It never waits, so it never blocks behind another holder and is never part of a wait cycle; inside the daemon nothing runs beside it (the serial daemon of item 1).
4. Finalize keeps R1c-1's order: fsck's transaction commits first, then the top's root flock, then seal's `BEGIN IMMEDIATE`, and S's entry locks only after the seal (R1c-1 §5.9). Partial fsck progress adds no lock.

**Holders of a sealed layer root's flock** (Keystone fix (3)). The #240 lock of `docs/sandbox.md:603-613` (`write_overlay.rs:7424`), with R1c-1's three added holders (`r1c1-impl docs/sandbox.md:615-622`) and R1c-2's one:
- seal, unseal and commit: exclusive, waiting without a deadline (the supervisor's own seal in finalize waits up to `FINALIZE_WAIT`, R1c-1 §5.3);
- a `--lower` bundle cache hit: shared, while it checks and verifies the entry;
- a cache fill or `overlay unpack` (`publish_layer`): exclusive, across its rename and mode restore;
- finalize's S on each lower: exclusive, bounded by `FINALIZE_WAIT` (R1c-1 §5.6);
- **`forget`**: exclusive and non-blocking, on `retained/ID/overlay` (item 3).

An `overlay seal` or `unseal` aimed at `retained/ID/overlay` while `forget` holds it waits, then finds no tree. Step 3 adds `forget` to the docs paragraph, which then names four more holders.

## 8. Risks

1. **Recovery trusts new descriptors.** An fsync error the previous run consumed is not reported to the restart's syncs (R1c-1 Risk 3, inherited), so an entry whose R4 failed in that run is acknowledged after a restart once both directory syncs return 0. On ext3, ext4, xfs and btrfs a failed metadata commit makes the filesystem refuse later writes, so the restart fails instead; ext2, admitted by R1c-1's allowlist under the same magic number, has no journal. The poison message and the restart docs make the restart the operator's statement that the storage was checked.
2. **Startup cost.** Before the daemon serves: up to `--max-retained` (4,096) `read_no_recovery` reads, two lookups per recorded entry (its base and `indexes/<base>/`), two directory syncs, one append per aborted record, and R3's fast path for at most one target. That fast path is one S over an entry and its lowers, which may wait up to R1c-1's `FINALIZE_WAIT` for a lower's entry lock that another process holds. Timed in the PR.
3. **Entries with nothing readable protect nothing** (§1.1, boundary 1). An entry with neither a record nor a readable database refuses no `forget`. Only an outside actor or a lost `retained.jsonl` makes one, and it is never served.
4. **`forget` takes no request ID.** A lost answer's retry answers `not_found`, meaning already forgotten. If the ID were drawn again and retained between the two calls, the retry would forget that new entry. An ID stays reserved while a stored `new` or finalize answer names it (R1a, R1c-1 §5.2). Under approval note (a) a retained entry's finalize records are pinned until `forget` ends the pin (F4); only then can R1a's caps evict them, so the ID stays reserved at least until those records are evicted. With request IDs on `new` or `finalize` (R1a's retry-safe mode for harnesses), nothing can therefore take the ID within a retry window. Without them, a redraw needs one specific value of 62⁶ (sweep 2, Claude B1).
5. **Mounts outside the supervisor are invisible to `forget`.** A grading or branch mount that uses `retained/ID/overlay` as a `--lower` holds no lock `forget` checks, and neither does an attempt of another supervisor, to which `<state>/retained/ID/overlay` is an ordinary lower path (its own place rule guards only its own state root). The root flock refuses only seal, unseal, commit and the cache's holders. Documented: unmount first, and do not lower one supervisor's retained layers into another's attempts (sweep 2, Claude N11).
6. **Downgrade.** An R1c-1 daemon refuses a `retained.jsonl` with `forgotten` lines (fail closed); documented order: move it aside, which keeps the trees and loses the records.
7. **R1c-1 is not merged.** Its names and lines may change (run 2 found most §4.1 lines moved since run 1); §4.1's facts and §5.9's notes are re-checked against R1c-1 as merged before step 1, and step 2 rewrites the R1c-1 restart assertions it lists.
8. **Damaged entries hold `--max-retained` slots** until forgotten, and a stray directory planted at `retained/ID` is deleted by `forget ID` (documented).
9. **Start-time refusals.** R0 (an entry in `retained/` that is not a private directory with a valid name) refuses the start and names the manual remedy; R1 refuses it only on a sync error; `reconcile` refuses it when it cannot remove a stale tree, naming the entry (Risk 12). A state directory off the allowlist starts with every entry damaged instead. A v1-only state can meet only the last, as today.
10. **Circular references from outside edits** need the manual repair (§1.1, boundary 2; §5.3).
11. **Departures from the source doc,** each for a ruling, R1c-1's design or a code fact: `forget` answers `{"forgotten": true}`; the statuses `retained_damaged` and `forgetting`; recovered entries are listed by v2 `list {all: true}` only (R1c-1's choice, which keeps R1a's U2); damaged entries are never deleted automatically; a record whose tree is gone is aborted at the next start; an entry busy at start answers `in_use` until a restart.
12. **Content an outside actor makes undeletable.** R1c-1's S opened every directory of a retained tree before its commit (R1c-1 §5.6), so only an outside actor can put a directory the daemon cannot open inside one. `forget` then fails at F3 with `io` naming that directory and stays `forgetting`, with everything else removed (D17). A restart after a crash past F1 is refused by `reconcile`, naming it the same way, as it is for any attempt holding such a directory. The remedy, in both messages and the docs: `chmod -R u+rwX` on the named path, then retry or restart (§3). F0 guarantees the checks `reconcile` makes before it deletes (row 20), not the deletion itself.
13. **`forget` on a poisoned filesystem waits for a restart** (§5.4), because a sync there proves nothing. An entry still in `retained/` is refused before F0 changes anything, and a `forgetting` one stops after F2. Until the restart the entry stays listed and still protects what it references; after it, a retried `forget` removes the first, and the start itself completes the second. The poison message already asks for that restart once the storage is checked.
14. **A base re-registered under the same name** (Keystone fix (4) checks registration and the folder, not the source). After a base is removed and registered again with another source or options, R2's checks pass and the entry is served. Composing it over the new base is refused by R1c-1's `diff` gate (`diff_failed`) and by R1b's base check for lowers; the fast path syncs the new `indexes/<base>/` and answers the entry's stored report, which describes the layer as it was sealed. The docs say to register a removed base again with its original source and options.
15. **An entry busy at start stays unserved for the whole run** (Keystone note 2). Each request naming it answers `in_use` until a restart, even after the lock is gone; a lock holder that never exits (a crashed `sqlite3` session left open, an `overlay unseal` stopped in a debugger) keeps it so until the operator stops it and restarts. The message says so. A cut-off finalize whose entry was busy at that start answers `interrupted` and is finalized again under a new request ID.
16. **F4's and G1's host prerequisites.** `user_allow_other` in `/etc/fuse.conf` (or root), `git` and `python3` for F4, beside R1b's FUSE gate, and `python3` for G1. The source doc already requires `user_allow_other` for its FUSE tests (row 24), and under the before-merge flag a missing one fails, so the author's FUSE host must provide them.
17. **`remove_contents` is shared** with the stage sweep of `overlay pack` (row 9). D17 changes only what it returns, never what it removes, and the sweep ignores the result; the sweep's tests pass unchanged.
18. **F4 compares a writable top's view with the same layer's view as a sealed lower.** Any difference it finds (a mode, an owner, a size) is a defect of the documented grading flow: it is fixed in this slice or taken to Keystone before merge, never hidden by loosening the comparison.
19. **One R1c-1 answer changes** (§1.1; note 2). A retry of a retain that never committed, whose attempt was destroyed, answers the not-served `invalid_request` in the run instead of R1c-1's `not_found`, until a restart aborts its record or it is forgotten. A harness that treated R1c-1's `not_found` there as final now sees a refusal first and `not_found` later; R1c-1's T22 and its docs row are rewritten in step 2, and the CHANGELOG names the change. It needs R3 to fail with its `aborted` append failing too, so it is rare.
20. **"Every later retry answers the same" has one exception** (Claude N3): moving `retained.jsonl` aside can turn a `not_found` (a live record of another instance) into the not-served answer for the tree that record named, now unrecorded. It never becomes a report: that tree is another instance's layer, which no record of the target's instance matches (R2 check 3), even one restored from an old copy of the log; the docs say so (§5.8).

## 9. Not taken

- **Identity matching of rows that name no retained path** (by `layer_digest`, `sealed_at` and prefix equality; the blocked plan's digest read-back, and a first suggestion while drafting this plan). Three code facts make it unnecessary:
  - R1c-1's place rule admits only `<state>/retained/<ID>/overlay` as a retained lower, and the child records canonical paths (row 4);
  - a dependant composes by reading the paths it recorded (row 5);
  - `forget` deletes only `retained/X`.

  So a row naming a cache directory or a user's copy loses nothing when X goes, and matching it would make dependencies that match no breakage, plus ambiguity between byte-identical copies. Keystone's ruling keys on "attempt ID or path", with `sealed_at` and prefix as confirmation.
- **A length condition on ambiguous references** (this plan's first draft; sweep 1, Codex B2). The ruling requires refusal, and lengths read back from rows prove nothing about an unconfirmed reference. The cycles it avoided only outside edits make, and those get a documented manual repair.
- **"An unknown entry may depend on anything"** (the blocked plan's rule that unknown entries refuse every `forget` of a known entry): it deadlocks against any entry that names the unknown one (§1.1, boundary 1).
- **Counting records without a tree in `retained/` as dependants** (sweep 1, Claude N5, which allowed either choice): they hold no layer anything could compose. Counting them would also undo the manual repair, since a removed tree's record would keep refusing.
- **Refusing the start on a state directory off the allowlist** (the first draft): it left no way to run `forget` (sweep 1, Claude N7).
- **Running S at recovery for every entry:** §5.2.
- **Request IDs on `forget`:** §3, Risk 4.
- **Serving unrecorded trees again** (re-adoption from their databases): no instance, no report; §3.
- **Persisting poison marks across restarts:** R1c-1 Risk 3 keeps them in memory; R1c-2 does not change R1c-1's design.
- **A start-time device check across `retained/` and `attempts/`** (the blocked plan's `st_dev` check): R1c-1 dropped it; a cross-device `retained/` fails R1c-1's R3 with `EXDEV`.
- **A new error code** for unconfirmed references: `in_use` with a message naming the referrer and the remedy, as for every other dependant.
- **Showing prefix lengths in `list`:** the v1 attempt shape has no room; "forget what the refusal names, then retry" needs none (sweep 1, Claude N9).
- **A waiting flock in `forget`:** `LOCK_NB` keeps the serial daemon from waiting on another process.
- **Keeping only the first try's `repaired:N`:** the total counts every repair that took effect (§5.5).
- **Writing `forgotten` before removing the tree** (the blocked plan's F3 before F4): a failed removal would leave a tree in `attempts/` whose record had already ended. The record goes last.
- **Deleting a tree in place, without the rename back** (an alternative to sweep 2, Codex B1's fix). After F2, one durable rename decides the tree's fate, and every later step happens in `attempts/`, which every start clears. An in-place deletion would instead depend on the durability of every directory it changes, and a power loss could bring back any part of the tree in `retained/`. F0 makes the rename safe instead.
- **Syncing F0's root only after an unlink** (sweep 3): a retry after a failed sync finds no `mnt` left to unlink, so it would need a per-run mark to sync again. One directory fsync per `forget` costs less than that state.
- **Finishing `forget` on a poisoned filesystem in the same run** (sweep 2's text): F3 would delete a tree whose rename back no sync proves, and a power loss could then put a partly deleted tree back in `retained/` whose database still passes §5.2's checks, so it would be served. The restart that the poison message asks for finishes it instead (Risk 13).
- **An F0 walk checking that every directory of the tree opens:** R1c-1's S opened every one before the commit, so only an outside actor adds an unopenable one (Risk 12). The walk would need a new inventory site for subdirectory opens, for that case alone.
- **R1c-1's kept-target re-read for an entry recovery found damaged** (run 1's D15 and T6: `not_found` when the tree fails it, a busy database included). Keystone note 2: a live record or a tree that may be the target's is not positively gone, and a busy read is temporary.
- **Treating a damaged entry whose record matches as kept, without re-reading it** (sweep 4, Claude #1's fix, which gave the busy case R1c-1's "kept, not served" answer from the record match alone), and any re-check that serves a damaged entry within the run: rejected by note 2, since it would serve a tree R2's sealed check never passed. R1c-2 answers from R2's classification instead: `in_use` while R2 found the database busy, otherwise the not-served `invalid_request` naming the check R2 saw fail. Neither says the result is kept, and only the next start's R2, which re-reads everything, can serve the entry.
- **`not_found` for a `forgetting` entry past a trusted F2** (run 1's D15): note 2's "forgotten" is F4's line; until then the record is live, so the entry gets the not-served answer.
- **Widening `IR-E0145-M01`'s reason to cover F0's root sync** (sweep 4, Claude #7's other option): F0 already holds an `open_root` descriptor of that root, the descriptor S syncs tree roots on.
- **Naming only the attempt root when a removal fails** (R1c-1's `remove_tree`; codex-4 #2 suggested documenting it): Keystone fix (7) requires the descendant, which D17 reports.
- **A grading argv built inside F4 instead of the recipe's own function:** the recipe and the test could drift; F4 and G1 run the documented function, and D1 pins its flags without FUSE.
- **Keeping R1c-1's `not_found` for its in-run orphan** (revise-0's §1.1 boundary 4): note 2 allows `not_found` only without a live record, and a later outside copy of the destroyed layer could have turned that `not_found` into `done` (run 2 sweep 1, Claude B1). D15's lookup answers it as not served until the record ends.
- **Reasons only in the refusals** (revise-0): Keystone fix (4) lists the entry with its reason, and the v1 attempt shape has no place for one (run 2 sweep 1, Codex B1); the additive `reason` member carries it.
- **A shell grading block** (revise-0): a failure inside its process substitution left the lower list empty and still mounted, its line-based read split a path holding a newline, and its hand-written JSON did not escape the state path (run 2 sweep 1, Codex B2 and N4). The Python function has no shell between its steps.
- **Grading as the current user's IDs** (`$(id -u)`, revise-0): those equal the workers' only when the grader is the user that registered the base (Claude N9); the function takes the registered IDs.
- **Adding the mount point to the Mounter's cleanup error in `reconcile`** (revise-0): for a failed mount-table read it names the wrong path (run 2 sweep 1, Codex B3); D18 names the path where the call fails.
- **Routing `cleanup` and `detach` through R1c-1's `mounted()` seam** so a test can fail their read: it would change what R1c-1's `ProcessMounter` tests that set `mount_table` do during `cleanup` and `Drop`; D18's own fault point reaches the same read instead.
