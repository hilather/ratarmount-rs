# Python ratarmount vs Rust ratarmount-rs — benchmark comparison

Generated by `benchmarks/compare-python-vs-rust.sh`.

**Snapshot:** 2026-08-27 · ratarmount-rs **v0.1.27** (`850be87`) vs Python ratarmount **1.3.0**. BIG=1 suite (default fixtures + x10 blob + `.tar.zst` / `.tar.lz4`).

**Regenerate published suite:** `BIG=1 ./benchmarks/compare-python-vs-rust.sh` (needs FUSE, `RATARMOUNT_PY_ROOT`, `zstd`, `lz4`). Writes `python-vs-rust-results-big.{csv,md}` and copies to `python-vs-rust-results.{csv,md}`.

Methodology (aligned with upstream mounting/bandwidth benchmarks):

- **Cold mount**: recreate index (`-c`), wall time until FUSE mount is usable.
- **Warm mount**: reuse SQLite index, wall time until usable.
- **Random access**: median of N `cat` timings on randomly chosen files (N=15; N=3 on BIG blobs).
- **Random 64KiB pread**: median of 15 `seek+read(64KiB)` on the bandwidth member (true random I/O on large blobs).
- **find**: wall time of `find <mount>` (metadata storm).
- **Bandwidth**: sequential `cat` of a large file, MiB/s.
- Both tools run with `-f` (foreground FUSE) for comparable process measurement.
- Peak RSS sampled from `/proc/<pid>/status` `VmHWM` after mount is ready.
- Large `.tar.zst` is **multi-frame** (independent frames); large `.tar.lz4` uses 4 MiB independent blocks.

**Relative** names the **winner** and by how much (never labels a loss as a Rust speedup).

## Notes / caveats

- Values **below 1.0×** in the summary mean **Python is faster / better**, not a Rust win.
- Compressed TAR (`.tar.gz`/`.bz2`/`.xz`/`.zst`/`.lz4`): Rust uses seekable outer codecs (`SeekableBody` / multi-frame maps / independent lz4 blocks) for indexing+mount; plain single-file `.gz` etc. still materialize. Python uses rapidgzip / indexed codecs / block-parallel paths with true bit-block maps in some cases.
- Random access and find on uncompressed TAR/ZIP remain the fairest apples-to-apples metrics.
- `rand_pread_64k` is the right random-I/O metric for `large-*` blobs; full `cat` of those members is sequential bandwidth.
- Sequential-bandwidth geo-mean still includes tiny members when present; prefer `large-*` rows over `nested-tar.tar`.
- Results are single-run wall times on this host; treat as directional, not formal publication numbers.
- Multi‑GiB/s sequential numbers are FUSE + page cache (the 640 MiB blob fits in RAM), not a disk-speed claim.
- Extreme `.tar.lz4` 64 KiB pread ratios mean Python is not using a cheap independent-block seek on the large member (hundreds of ms per 64 KiB vs tens of µs).
