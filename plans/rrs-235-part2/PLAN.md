## Replan decision: drop receipt supersession and RetainOffline redesign

Keystone's ruling of **2026-11-06** is binding: the previous plan6 draft is **not ACCEPT-as-is**. Receipt supersession could discard replay protection for retained raw overlays: after A → B, retry A could become an unchecked raw commit (`identity_checked: false`) because B replaced A's receipt. That is a security downgrade and is not waivable. This revision resolves the scope error by removing that mechanism, not by accepting its risk.

**DROPPED:** overlay/commit receipt supersession, latest-operation receipt replacement, and any receipt cleanup or index-publication transition that resets or orphans earlier overlay identity/replay protection. Also dropped is the plan-invented **RetainOffline/raw-overlay receipt-protocol redesign**: the commit-operation envelope and new commit-state namespaces, frozen-delta receipt manifests, durable overlay edit-revision allocator/`LegacyNoRevision`, persisted rolling-generation completion receipts, and remote commit replay records/spools. These were proposed architecture, not facilities already on main. They are out of part-2 scope and are not required to route index opens through #239's `open_checked`. There is no implementation step or acceptance dependency on bringing them back.

The retained change is one shared symlink-refusing index path and lossless error transport. It must preserve every existing identity, replay, hashing, journal-ownership, required-record and sealing guarantee on main. Index installation may retain durable `Done` bookkeeping solely to finish companion retirement and admit later checked opens; that bookkeeping has no overlay identity or replay authority and never replaces an overlay/commit receipt.

**Non-negotiable invariant:** if a remaining mechanism participates in overlay identity/replay protection, after A → B, retry A must retain A's protection or require a fresh successful identity check. It must never run with `identity_checked: false` because a later receipt replaced earlier evidence. The preferred design below introduces no such mechanism. If implementation discovers that one is unavoidable, return to the architecture gate; do not expand this plan into a RetainOffline redesign or waive the invariant.

## Shared acquisition contract

Names below are illustrative; the responsibilities and outcomes are required. The shared API exposes connection, managed-byte-read, install/publication, and removal operations over an operation-owned index-path context. Its connection owner retains that context through the final SQLite close. Callers supply the requested spelling and intent. They do not canonicalize the complete path, pre-filter it with `exists()`/`is_file()`, decide symlink policy, or perform a raw fallback open.

### Parent-only resolution and classification

1. Retain the requested path for diagnostics. Treat it as a filesystem name, not a caller-supplied SQLite URI. Reject directory-like selectors with no ordinary final filename rather than silently changing which component is final.
2. Resolve **only the parent directory**, then join the untouched final filename. For a relative basename the parent is `.`. Create missing parent directories only for intents whose existing contract permits that, and resolve the resulting parent before acquisition. Never canonicalize the joined index name. Remove upstream whole-path canonicalization from lookup, prepared, digest-cache, and selected-index byte paths.
3. Use `symlink_metadata`/`lstat` on that final name and literal SQLite companion names. Existing and dangling final symlinks are the same terminal refusal. Parent symlinks remain valid, including macOS `/var` aliases. A non-regular final component or an uninspectable required path is refused; it is not an absent cache.
4. A genuinely absent final name is permitted only for an explicit create/install intent, or returned as absence for optional lookup/patch intents. It must not be inferred from following a dangling link. Existing-file acquisition must not recreate a vanished file.
5. For SQLite connections, call `checked_open::open_checked` with `SQLITE_OPEN_NOFOLLOW`, the appropriate `NameMode`, and existing/fresh expectations from the shared classification. Classify checked-open refusals without losing identity evidence or retained-descriptor handling. Recheck named state on failure using #239's refusal machinery.

The non-mutating coordination-placement preflight below precedes any permitted parent-directory creation in step 2; it must not first create a selected parent inside the forbidden coordination subtree. Final-symlink classification keeps diagnostic priority without mutating either tree.

Revalidate a selected final name and its companions immediately before publication, replacement, or unlink. A symlink present then is left intact, as are its target and companion targets. Preserve caller spelling in diagnostics while using the parent-resolved name for I/O. Identity mismatch is terminal. This retains #239's acquisition proof and adds guarded pathname mutations; it does not promise atomic protection from every hostile rename between a pathname check and rename/unlink.

### Connection modes and no-write behavior

All on-disk read-only opens refuse final symlinks; there is no read-only-follow exception or remaining intent question. Preserve the existing lookup modes inside the boundary:

- With no companions: immutable read-only acquisition of the admitted main file.
- With a live `-wal` and `-shm` and no journal: ordinary read-only acquisition, preserving visibility of committed WAL data.
- With incomplete companions or a hot journal: managed copies into an owned private directory, recovery there, and a connection to the private copy.

None of these lookup modes may create, recover, truncate, checkpoint, or remove files beside the original index. A terminal refusal in one mode must not fall through to another. Prepared opens keep their immutable URI construction, companion restrictions, and identity checks. Caller-controlled URI parameters, `vfs=`, and shared-cache flags cannot bypass the selected policy. Explicit in-memory indexes remain in memory and acquire no selected disk inode; they are not an automatic fallback after refusal.

These lookup heuristics are not source-consistency or immutability proofs. In particular, companion-free immutable lookup must not be reused to stage a mutable installation source or assign a content-addressed publication ID. The installation/snapshot contract below applies independently of the lookup mode.

### Connection lifetime, refusal and SQLite teardown

**Admission is a connection-lifetime obligation.** Return an owned checked-connection wrapper, not a detachable raw `Connection`. It owns the admitted main/companion identities, pathname generation, allowed mutations, and a latched typed failure. Install its registration before SQLite can acquire files, including failed-open cleanup, and retain it until all statements/transactions, the connection, WAL/shared-memory objects and owned cleanup have finished. A moved owner or close on another thread retains the same registration; a thread-local acquisition window alone is insufficient. Registrations for multiple connections to one database are reference-counted and generation-aware. No callbacks hold the registry mutex while calling SQLite or a filesystem operation that can reenter it.

SQLite-owned pathname work is mediated inside this same boundary:

- On supported Unix, extend the existing early-installed, verified syscall wrappers with `unlink` mediation and lifetime admission for companion `open`/`stat` calls. The pinned Unix VFS uses its `unlink` syscall for both `xDelete` and the direct unlink inside `unixShmUnmap`; wrapping `xDelete` alone misses the latter. Before forwarding a selected-name removal, classify without following and compare that generation's admitted identity. Before opening/creating a named companion, enforce nofollow and the allowed existing/exclusive-create intent. Record created identities through the SQLite-managed acquisition, without raw alias probe descriptors. Unexpected names/types/identities latch the shared failure and deny the syscall. An obsolete generation has no authority over new-generation names.
- On Windows, use the checked-family VFS/I/O-method adapter and handle-creation protocol below. Delegate the underlying Windows locking/I/O while mediating actual handle creation, `xDelete`, companion opens and delete-on-close, and force `xShmUnmap(deleteFlag = 0)` when deletion is not admitted. Preserve the stated path-type-only checks; do not claim Unix inode evidence. Reject any selected-file delete-on-close request that cannot be mediated. All configured SQLite builds, including SQLCipher, must prove coverage of their actual creation and cleanup paths; an unsupported mechanism returns `AcquisitionUnavailable` before exposure.
- Configure selected connections with `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` before any schema/WAL work and verify the result. Keep persistent-WAL behavior while teardown is not authorized; these controls suppress implicit close cleanup but are not the sole guard for journal-mode changes, explicit checkpoints, or error unwinding. Lookup connections never receive authority to mutate original names. Private recovery/staging connections receive authority only over their proven owned files. Healthy writable finalization performs its checkpoint/companion maintenance explicitly under admission and preserves the established locking/mode and successful-publication contracts.

Revalidation failure first **poisons** the lifetime context, before unwinding any connection. Stop new SQL, checkpoint, journal-mode changes and pathname mutations through it. Do not try to cure refusal with `journal_mode=DELETE`, a checkpoint, or raw unlink. Close with automatic checkpoint/deletion suppressed; callbacks must still deny removal of refused/replaced main or companion names while releasing SQLite-managed locks, mappings and descriptors normally. A callback refusal is latched even when SQLite ignores its unlink return code. Fallible `finish`/close reads that latch before an operation reports success and retains any primary typed failure. `Drop` cannot return an error, but must enforce the same deletion suppression and preserve/report a late cause through the owner or pending-maintenance record. Do not leak a connection, operation owner, lease or normally closeable descriptor to avoid teardown. This requirement preserves #239's deliberate retention of rejected regular/indeterminate acquisition descriptors: closing those aliases can release another connection's process-wide locks. Keep that existing retained-descriptor policy and its regression; do not force-close them or redesign #239 here.

Required proof: acquire a writable WAL connection, replace each of `-wal` and `-shm` with existing and dangling links, detect refusal, then drop the **entire** operation, including retained connections and temporary guards. Links, targets, target modes and bytes remain intact; locks and permits are released. Repeat with main-name replacement, failed validation/open, explicit close, multiple connections, cross-thread drop and private staging cleanup. This covers mutations after `open_checked` has returned and after the caller has already selected the refusal result.

### Managed bytes, install destinations, and ownership

The shared `read_selected` operation performs parent-only resolution and final-name refusal **before** acquiring a `ManagedReadCursor`. Its internal selected-index cursor entry point must accept the admitted name/expectation and avoid today's full-path canonicalization. It opens with final-component nofollow semantics, requires a regular file, and checks the acquired identity where the platform supplies it. It must not resolve a final link between classification and acquisition. Name/identity changes during acquisition or copying fail through the same typed contract.

This remains a managed reader: preserve SQLite's VFS ownership, parked-descriptor/close behavior, reader admission permits, and protection of locks already held by SQLite. The cursor itself takes no transactional lock. Neither its ownership nor a shared parent lease prevents source writes/checkpoints, and inode revalidation cannot detect torn bytes within one inode. Do not replace it with `File::open`, `std::fs::copy`, or a probe descriptor whose close could release this process's SQLite locks on an aliased inode. The selected-index variant does not change symlink semantics for unrelated archive readers. Byte acquisition creates no SQLite companions merely to serve bytes.

Remote/local installation uses a shared install operation for **both source and selected destination**. Resolve and classify the destination before copying; existing or dangling destination symlinks cause refusal before truncation, chmod, unlink, or target writes. Replace selected-index uses of ordinary `copy_create_or_truncate` with an admitted consistent source staged into an exclusively owned sibling temporary. The staged database must be synced and self-contained: no WAL/journal from the source or destination may be needed to interpret it. Never open the selected destination with ordinary create-and-truncate flags. Existing regular and empty destinations remain replaceable under the publication protocol below. Preserve source permissions through the staging handle and the established umask/mode policies; document staged replacement and its busy/pending outcomes. A refused destination must not silently select the fetched path instead.

**Choose source consistency before companion classification or any copy/hash used for installation.** An existing local database is mutable by default, even when opened read-only, its inode is unchanged, or no companions currently exist. Stage every mutable source through a checked consistent SQLite snapshot, preserving `snapshot_index_into`'s ordinary-locking rule for both initially companion-free and live-WAL sources. Establish and retain SQLite's read-transaction/snapshot protection for the whole logical snapshot; include committed WAL data at that snapshot boundary. A writer starting after classification, switching journal mode or checkpointing during staging must yield one consistent committed database or a typed refusal/`Busy`, never a raw main-file copy. Source and snapshot connections retain their lifetime admission and teardown protections. Existing incomplete-companion/hot-journal snapshot refusals remain refusals; the lookup private-copy path is not an installation fallback. Adapt snapshot output ownership to the exclusive staging guard without weakening this consistency rule or allowing recovery/writes beside the original source.

Raw managed byte copying is reserved for **proven immutable artifacts**, such as an exclusively owned completed download or a privately finalized SQLite snapshot whose writers and writable aliases have been closed and cannot be readmitted while copied/hashed. An absence check, file mode, `immutable=1` flag, observed hash or caller assertion alone is not that proof. The admitted immutable owner must retain the no-writer guarantee throughout copying, hashing and publication. A mutable hardlink/alias invalidates that proof. Staging precedes destination publication exclusion, so the later exclusive parent lease cannot retroactively protect the source copy. Once the owned snapshot/artifact is complete, release or transfer the operation's source holders under the existing ordered-lease protocol before requesting destination exclusion; never wait on its own shared holder.

Required regression `regression_235_part2_install_writer_after_no_companions` uses a deterministic barrier after observing no source companions, then starts a child SQLite writer on the same inode, commits multi-page changes and checkpoints before/during staging. Assert the installed database passes `PRAGMA integrity_check`, contains a whole committed generation with matching row/checksum invariants and obeys the defined snapshot cutoff; a schedule committing before the snapshot read must include that commit. No mixed pages or lost committed-WAL rows, raw-copy fallback, source recovery mutation, or released holder lock is allowed. Repeat the source-consistency controls through local and remote-install callers; an owned immutable-artifact control permits exact managed copying.

Exclusive ownership must be real: create staging files with `create_new`/`O_EXCL` (or an equivalent exclusive temporary API), retain an ownership guard and created identity, and pass that owned empty file to checked acquisition as an existing file with emptiness allowed. `Expect::Fresh` alone does not prove exclusive ownership. PID/sequence names may collide; never truncate, adopt, or delete a collision. Cleanup removes only names still belonging to the operation's guard, including its SQLite companions. Reaping by PID/name alone cannot authorize deletion of an unproven artifact; leave unproven leftovers for explicit cleanup. Preserve cold-index `0644 & !umask`, published-temp modes, private-copy exact modes, and the existing companion-mode rules.

Replace the PID/name-only authority in `reap_stale_writable_tmps`. Update/rename `regression_create_writable_reaps_same_pid_tmp` to assert preservation of an unowned same-PID leftover, and add a dead-PID control. Keep the live-temporary preservation pin and prove that a recorded, exclusively owned artifact can still be cleaned. A previously green reap expectation is not a reason to retain unproven deletion.

Close exclusive-create/copy output handles before a SQLite connection takes locks on that staged inode, or transfer ownership through the reviewed SQLite-managed mechanism. The ownership guard must not later close a raw alias descriptor and release a live connection's process-wide locks. Staging creation and cleanup tests retain the existing cross-process lock probes.

### Installation intents and content-addressed artifacts

The shared primitive has distinct **mutable-index** and **immutable-artifact** installation intents. The intent is selected before staging and carried through publication, verification, reopen, lifetime teardown and recovery. Source consistency is independent: a mutable source always needs the checked snapshot above, including when its destination will be immutable. The mutable-index intent preserves existing writable reopen behavior only for a working index whose bytes are not promised to match a publication ID.

For a newly published content-addressed artifact, snapshot a mutable input into private ownership, complete every required checkpoint/journal-mode conversion/schema finalization there, close all writable SQLite owners and sync the self-contained result **before computing or assigning `index_id`/`etag_sha256`**. Freeze that owned byte sequence, then stream its SHA-256 through admitted managed acquisition. The pin filename, pointer fields, uploaded blob identity and installation's expected digest all refer to those exact bytes. `publish_index_pointer` and `IndexPointer::for_blob` consume the same frozen artifact/ID rather than independently hashing a sidecar that may change between calls. A live-WAL source is snapshotted with its committed rows before the resulting artifact receives its ID.

For an already-known/requested ID, including `snapshot_index_id` and fetched hash-addressed blobs, verify the admitted immutable source bytes against that ID and preserve them exactly. Do not run `VACUUM`, checkpoint, schema setup or WAL conversion on those bytes under the old ID. If a mutable source needs snapshot/finalization that changes bytes, a new publication computes its ID afterward; a request bound to the old ID fails rather than silently changing the ID or installing different bytes. A DELETE-mode artifact must retain its DELETE-mode bytes; merely enabling WAL would violate the contract even if logical rows are unchanged.

**Immutable-artifact installation permits no writable finalization.** After freezing/ID assignment, no phase, checked reopen, verification, successful close/drop or recovery may enable WAL, change journal mode, migrate schema, fill digest/side tables, checkpoint, or otherwise alter those bytes. Verification/reopen uses only checked immutable read-only or non-writing managed/lock-only objects with the existing cleanup suppression. No new artifact companions are created; an old destination's companions are still retired under the common protocol. The installation record and durable logical-main role retain the immutable intent and expected digest so restart or a later ordinary writable/digest-cache open cannot downgrade it. A working index that needs writes uses a separate owned mutable copy, without an inode shared with any pin. Never hardlink an immutable pin to a mutable working database; hardlinks between proven immutable owners require the same no-writer guarantee for every alias, otherwise use an owned managed copy.

The frozen digest must match before publication, after the guarded rename/verification, after full owner teardown and on fresh-process `resolve_index_id_path`/`bind_local_index_id`. A mismatch refuses or retains the structured pending/unknown installation outcome as appropriate; it cannot be excused as expected finalization drift, repaired by renaming the ID, or hidden by a mutable well-known fallback. Publish the pointer only after the matching immutable pin is durable and verified, and never advance it on a failed/pending pin installation. Keep existing pin retention policy through guarded removal; these blob IDs are not overlay replay receipts.

Required regressions exercise `publish_index_pointer` -> `snapshot_index_id` -> fresh-process `resolve_index_id_path`/`bind_local_index_id`, for a proven immutable, pre-hashed DELETE-mode artifact and for a live-WAL mutable source with distinguishing committed rows. Hash the exact finalized bytes, then assert pin name, pointer `index_id`/`etag_sha256`, installed bytes and fresh-process hash agree after verification, teardown, restart/recovery and a second publication. Preserve earlier pins/terminal records under their respective retention rules. Test known-ID mismatch, attempted writable reopen/digest fill, and later writes/checkpoints to the separate mutable source; none may modify an immutable pin. Compare exact byte hashes as well as logical rows and integrity; a rows-only assertion cannot catch WAL-header drift.

### Stable coordination storage and lease failure

Use a fallible, absolute-root variant of `ratarmount_index::local_cache::platform_cache_root()` for coordination. Honor a nonempty absolute `XDG_CACHE_HOME` override as `<XDG_CACHE_HOME>/ratarmount`; otherwise use `<HOME>/Library/Caches/ratarmount` on macOS, `<LOCALAPPDATA>/ratarmount` on Windows, then the helper's `<HOME>/.cache/ratarmount` fallback where permitted, requiring absolute home paths. Linux normally uses that HOME fallback. A configured relative root, missing usable platform home, or unverifiable/unavailable private directory is `AcquisitionUnavailable(CoordinationStorage)`. Do not inherit the helper's `./ratarmount` fallback, substitute a temporary directory or choose a working-directory-dependent root.

The stable root is `<platform-cache-root>/coordination-v1/`, with `index-namespaces/<hash-of-parent-directory-identity>/` for the namespace gate, lifetime lease, durable role ledger and digest-lock support artifacts described below. No remote commit records or replay spools are introduced. **Do not key exclusion by a hash of the requested final-name bytes.** Resolve aliases of the same parent to one OS directory identity (volume plus directory identifier where needed); the parent identity is not a replaceable database inode. If it cannot be established, return unavailable acquisition. Canonicalize the established parent/root consistently, validate private per-user ownership/permissions and acquire/create the final coordination entries without following links, only after the placement preflight below succeeds. These paths and role claims are coordination state, excluded from ordinary index/blob cache eviction, quota cleanup and temporary-spool reaping, including when no persistent index is requested. Never unlink/recreate a live lease or operation lock.

The supported coordination scope is participating processes of one OS user on one host, using the same resolved root and target-key rules. Existing environment overrides are the configuration mechanism; all participants must use the same values. Different users, hosts or deliberately divergent roots do not share these leases; arbitrary concurrent clients bypassing this protocol remain unsupported. Failure to create, validate or lock the required lease storage fails the open closed with `AcquisitionUnavailable(CoordinationStorage)` (or `Busy` for actual contention), before admitting any selected index. Skipping the lease is forbidden for connection and byte-read owners alike. Final-symlink classification retains its stated diagnostic priority.

### Global coordination placement is refused inside content trees

**Decision: the actual resolved `coordination-v1` subtree must be disjoint from every scanned directory base and mutable/raw overlay root.** Refuse either containment direction, equality, and equivalent/aliased placements. An absolute `XDG_CACHE_HOME` inside such a tree is therefore not an admitted configuration, even if current exclusion lists or filters would hide it. The installation suffix does not match this global subtree; do not claim that extending its predicate protects it. Prepare one shared, non-mutating layout context containing the prospective resolved coordination root, all directory-base and overlay roots, and selected main/companion/installation paths. Establish it before directory-base digest creation/comparison, overlay DB/marker creation, source serving, payload collection, reset, or any index-coordination mkdir/ledger/lock creation. Register the complete content roots at source/overlay admission even when the first index will open lazily; do not wait until a nested request has already exposed the directory. A route acquiring no selected disk index and using none of these support artifacts gains no new commit-coordination or receipt requirement. Reopen and offline verbs repeat the read-only check before accepting recorded exclusions or changing anything. Adding a content root to an existing session requires the same check before exposing it. Direct index-library users with no content roots still supply their selected paths and obey the selection restriction below.

Resolve existing directory ancestors and compare directory identities and filesystem-equivalent components, including symlinked parents, native case/normalization aliases and supported mount aliases. For a not-yet-created root, resolve the nearest existing ancestor and validate the remaining ordinary components without creating them; pin/revalidate that evidence before later mkdir. A lexical prefix check or whole-index canonicalization is insufficient. If disjointness cannot be established, return `AcquisitionUnavailable(CoordinationStorage)` with a placement diagnostic naming both roots. Do not create a temporary root, choose another cache location, add a digest exclusion, or recommend `--force-base-mismatch`. Require a disjoint configured cache root. Out-of-band changes to mount topology remain outside the participating-process guarantee; revalidate layout evidence before creation/mutation.

The same shared layout guard applies when a directory source or overlay later resolves a host traversal through an alias: a target entering global coordination is a conflicting subtree admission, refused before node hashing, enumeration, file open or mutation. An in-tree symlink to otherwise external coordination storage cannot expose its artifacts by direct descendant access. Retain nofollow walks; an opaque user symlink entry does not authorize following its target. Inspect relevant mounted-directory aliases during the read-only placement proof, or refuse when their disjointness cannot be established. Do not add frontend-specific path filters for this rule.

The shared boundary reserves the **actual resolved coordination subtree and its support roles**, independently of content suffixes. An ordinary selected main, any literal companion, installation namespace, or local publication target/state path may not enter or replace that subtree or an internal artifact, or destructively replace/remove an ancestor containing it. Apply this to explicit `--index-file`, optional/absent selections, byte reads, install, publication and removal before opening a file or creating its parent. Only a coordinator token for an exact owned support artifact permits its internal acquisition; it is never a selected SQLite main. Alias access must receive the same refusal. A file already used as a gate, lease, ledger, digest lock or installation record cannot be selected as an index to collide with its owner. Unrelated content merely named `ratarmount` or `coordination-v1` outside the resolved subtree stays ordinary content.

These refusals keep the global tree out of serving, weak/strong identity, bundles, commit payloads and reset by preventing admission of the conflicting source/layout. They are required at every such entry, rather than allowing an admitted overlapping tree and hoping later scans omit it. If preexisting global coordination state is discovered inside a proposed base/overlay, refuse before digest comparison, serving or cleanup and preserve it intact; no recursive wipe or migration is authorized. Eviction/removal of a cache ancestor must separately preserve the actual subtree and its stable locks. A later attempt to admit the overlapping content tree still refuses even after a ledger owner exits.

Required placement tests set `XDG_CACHE_HOME` so coordination would be inside a directory base and, separately, an overlay (also test a content root inside existing coordination storage). Cover initially absent storage, existing ledgers/support artifacts, symlinked-parent and native-equivalent aliases, an in-tree link/bind alias to external coordination, lazy first admission, remote selected-index acquisition, reopen, digest/pack/commit entry and reset/error cleanup. Refusal precedes every creation or content mutation for an overlapping layout; alias traversal never reads or modifies coordination artifacts. Preserve preexisting bytes, recorded weak/strong digests, rows, lock identities and existing identity/replay evidence. A disjoint-root control admits lazy publication, changes ledgers, reopens and resets ordinary payload normally. Explicit index paths aimed at existing and absent gate/ledger/digest-lock slots, including aliases and ancestor replacement, refuse before SQLite/ordinary-file acquisition and preserve a held child-process lock. No test may treat a placement refusal as successful support for in-tree global coordination.

### Complete namespace exclusion and conflicting roles

For selected main name `m`, the protected set is **`{m, m-wal, m-shm, m-journal}`**, plus its installation namespace. All connection, byte, publication and removal intents participate, including optional/absent paths. Use a deliberately coarse **per-parent** publication lease so overlapping or equivalent names always share exclusion, without relying on a final-name hash. Healthy owners retain a shared parent lease; installation, retirement and removal require the exclusive parent lease. Unrelated indexes in one directory can therefore make publication `Busy`; document this conservative serialization. A later optimization must retain this contract and receive review.

Each parent namespace has a stable, short-held admission gate and a versioned, synced role ledger. **First initialization is distinct from lost evidence:** under the stable `index-namespaces` initialization guard, exclusively create a previously absent per-parent namespace, then create/sync its gate, lease and empty ledger before registering roles or exposing an owner. Serialize concurrent first admissions; only the successful exclusive creator can initialize it. An already present namespace with a missing, unreadable or corrupt ledger, including partial initialization after a crash, refuses and preserves evidence. It is never treated as new or rebuilt from filenames. Keep initialized namespaces through eviction/removal so later missing-ledger detection remains meaningful.

Under the parent admission gate, compare the complete requested set against existing claims, durably register its roles before exposing the first owner, and obtain its lifetime lease. An installer retains the admission gate while draining holders and obtaining exclusive publication exclusion, so a new owner cannot slip between the ledger check and retirement. Role-ledger updates do not require upgrading other healthy shared owners' leases. For several parents, acquire gates/leases in directory-identity order; release and reacquire the complete set rather than upgrade out of order. Transfer the operation's own staging/read holders through this protocol so it never waits on its own shared lease. Coordination support artifacts, including digest locks, have separate protected internal roles and are never inferred to be user-selected mains.

The ledger records a logical main and each name's role/owner, including absent companions. **A name cannot be one selected main's companion and another selected main**, nor can different logical mains claim any overlapping set. Return terminal `NamespaceConflict` with both requested mains, the conflicting name and roles, before SQLite open, truncation, retirement or removal. This is not transient `Busy`, cache corruption or permission to discard either main. Selecting a file called `db-wal` remains possible when its complete family is disjoint; admitting `db` then conflicts, and vice versa. Main selections have no filename-extension whitelist.

Claims outlive connection close, process exit and terminal index-installation records. Otherwise closing `db-wal` would let a later `db` installer delete that other selected database. Only explicit shared removal/release under exclusive parent exclusion may retire a claim, after proving its owned main/companions and pending state have been resolved; no PID expiry, observed absence or cache eviction releases roles. Installation recovery retains the same logical roles across old/new main replacement. Private staging/retirement artifacts remain tied to their operation ownership and cannot independently become another selected main while claimed.

Name comparison is **filesystem-aware at the resolved parent**. Keep the requested spelling for diagnostics and the parent-only I/O rule; equivalent spellings resolve to one logical claim and one installation namespace. Append literal companion suffixes to the untouched requested main, and prove that this entire family maps to the ledger's claimed names under the filesystem's rules. Main-name equivalence alone is insufficient for Windows long/short aliases whose suffixed names may differ: refuse such an alias unless the complete family is proven equivalent. The comparison adapter must account for that directory's case and Unicode-normalization rules, including APFS normalization equivalence and Windows per-directory case behavior. An OS-wide lowercase transform, `canonicalize` of the final index, or a probe SQLite descriptor is insufficient. Use native non-mutating name lookup and the supported filesystem's verified comparison rules for existing **and absent** names. Refuse unsupported/ambiguous equivalence or Windows path spellings whose normalization/stream/device semantics cannot be represented by this component model with `AcquisitionUnavailable(NameEquivalence)` before acquisition; never assume byte sensitivity. APFS's default case-insensitive and normalization-insensitive behavior is documented by [Apple](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/FAQ/FAQ.html).

On Linux, `fstatfs` of the resolved parent selects a reviewed filesystem/configuration rule; raw component-byte comparison is a supported success path only when that rule establishes case sensitivity. For ext4, also query the parent directory's `FS_IOC_GETFLAGS` and require `FS_CASEFOLD_FL` clear; a casefold directory or an uninspectable rule returns `AcquisitionUnavailable(NameEquivalence)`. Filesystem type alone is not proof of a per-directory setting. Unknown types/configurations fail closed, without guessing that all Linux filesystems are byte-sensitive. The implementation records its supported rule table and native evidence; the ordinary ext4 non-casefold control must admit distinct `db`/`DB` families, including absent names. Tests for unsupported comparison cannot replace this usable success case.

Required evidence: two child processes select `db` and `db-wal` (repeat for `-shm` and `-journal`) in both admission orders, with real SQLite mains and distinct rows. The second conflicting role refuses; the first database and its companions remain intact. Repeat after the first owner exits and after restart to prove durable claims. Native case-insensitive macOS/Windows tests use `Index.sqlite` / `index.sqlite`, including initially absent names and equivalent Unicode names where supported, and prove one logical role/lease/installation namespace and serialized first/second publication. A case-sensitive control admits genuinely distinct names. Unsupported comparison must produce the typed unavailable outcome, not a separate lease.

### Digest locks are protected coordination artifacts

**Remove the sibling `.digest-lock` acquisition entirely.** For each admitted logical main, the durable ledger assigns a stable opaque logical-main ID. Place its hashing lock at `<coordination-root>/index-namespaces/<parent-id>/digest-locks/<logical-main-id>.lock`, with a recorded `DigestLock` support role. Equivalent main spellings use the same ID and lock; main replacement and process restart retain it. Neither a raw requested-name hash nor a current database inode selects this lock. The complete namespace contract includes this external support role, alongside the main/SQLite-companion/install family, rather than implicitly treating the old suffix as harmless.

All hashing, refresh and availability paths borrow an admitted digest context from the shared boundary. Replace `open_lock_file`, the `archive_digest_cache_available` open-and-immediate-drop probe, `HashGuard` acquisition/drop and their swallowed errors. Availability becomes fallible: a genuinely ineligible/read-only cache may remain unavailable/pending under its existing policy, but selected-path, support-role, storage and lock-acquisition failures retain their typed errors. An availability check may inspect protected metadata/capabilities or borrow a safely retained support object; it cannot independently open/drop an arbitrary writable file. Read-only peek stays nonblocking and does not create or acquire a hashing lock just to answer a cache hit/miss. Hashing that needs coordination must acquire the real cross-process lock or return the storage/lock failure; no warning-and-unlocked hash and no non-Unix `try_flock` no-op. Use the same verified native locking abstraction as coordination leases on Windows.

Support acquisition requires an exact internal artifact token, validated private directory, nofollow/exclusive creation for a new file, and proven ownership/identity for reuse. An unowned file, symlink, multiply linked artifact or changed identity is a refusal, never a create-or-open collision to adopt. Preserve the database-alias close discipline during acquisition, validation failure and teardown: use the shared managed/admitted support-file mechanism, with selected SQLite identities registered for the connection lifetime. Do not open a suspected alias as an ordinary data descriptor and then close it after `fstat`; use safe pre-acquisition identity checks and the existing rejected-descriptor retention policy where required. Protected artifact roles also prevent later selected-index acquisition of a held support object. A private pathname alone is not evidence that an arbitrary existing file is safe to close.

The digest owner retains its support-file guard through hashing/cache update and error unwind. Never unlink/recreate the lock on release, reset, normal eviction or restart; only the explicit guarded logical-role release protocol may retire it after all holders and pending operations are resolved. Establish/register the support role under the admission gate, release that short-held gate before waiting for the hashing lock, and reuse the admitted context for cache connections rather than reacquiring admission while holding the digest lock. Release/transfer the operation's own digest holders before exclusive publication so it cannot wait on itself. Keep cancellation and nonblocking peek behavior.

Digest-lock code leaves legacy `<index>.digest-lock` files **untouched**: no helper probe, open, copy, adoption, unlink or migration of their bytes/locks. They may be legitimate content or independently selected databases. `db` and a regular selected `db.digest-lock` therefore have disjoint families and both remain usable through ordinary checked database acquisition, in either admission order; their digest locks occupy different protected slots. If that legacy-looking name is explicitly selected and is a symlink, ordinary shared final-symlink refusal applies. A symlink there encountered only as the obsolete helper's sibling is ignored, not followed. Stop older binaries before upgrading participating processes; their sibling locking is not interoperable with the new coordination lock, and dual-locking the legacy name would reintroduce this hazard.

Required regressions use real SQLite `db` and `db.digest-lock` mains with distinct rows in both orders, plus existing/dangling legacy siblings and a sibling symlink to an already-open selected database. Exercise availability, peek, hash, refresh, failure and full digest-owner drop. A child-process contender must remain unable to obtain a held SQLite write lock before and after every probe/acquire/drop while the original holder's transaction remains held, then succeed after intentional holder release; intact bytes alone are not lock evidence. An expected cache-write `Busy` is acceptable during this control; releasing the holder to make the cache write succeed is not. Assert no support-file creation/mutation at legacy siblings and no new suffix chaining. Also cover equivalent-name shared lock identity, cross-process hashing exclusion/cancellation, restart/eviction retention, unsafe planted support artifacts and explicit selected paths colliding with the new lock slot. Native Windows must prove real interprocess exclusion rather than process-local bookkeeping.

### Windows handles retained through publication

**Do not release the destination SQLite lock to make rename succeed.** The checked Windows adapter must arrange rename-compatible handles when they are created. The pinned `winOpen` share mode omits delete sharing; [Microsoft's `CreateFile` contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea) applies delete sharing to rename as well. Merely delegating `xOpen` unchanged and wrapping `xClose`/cleanup does not satisfy this protocol.

1. Before concurrent use of the affected SQLite instance, install and verify checked-family wrappers for the Windows VFS `CreateFileW` and every enabled alternative (including `CreateFileA`; an unhandled `CreateFile2` path is unsupported). The pinned SQLite and SQLCipher Windows VFSes expose these through `xSetSystemCall`/`xGetSystemCall`. The adapter carries the lifetime admission context into `xOpen` and later I/O callbacks, including internal `winOpen` calls from shared-memory setup. A scoped callback context selects the already-owned registration; registration itself remains connection-lifetime, not thread-local. For admitted selected/owned files, add **`FILE_SHARE_DELETE`** to the underlying read/write sharing. For the owned publication candidate's lock-only object, also request **`DELETE` access** at creation. Keep all nofollow/type, exclusive-create, access and cleanup checks; unrelated SQLite opens retain their original flags. Do not patch system-call slots around each open or repair them after replacement. Unsafe/late initialization or an unverified/replaced creation path is unavailable acquisition.
2. Quiesce other destination/candidate connections, statements, WAL/shared-memory handles, mapped views and byte readers under the complete parent namespace lease. Close ordinary copy-output handles before SQLite locking. Retain checked lock-only VFS file objects for the old nonempty destination and self-contained candidate, using the underlying Windows SQLite `xLock`/`xUnlock`. Both surviving handle sets must be rename-compatible; an old handle cannot be retrofitted with delete sharing. Drain incompatible participating owners or return `Busy` before retirement. Never close a retained publication-lock object and substitute a raw alias lock. Old-generation cleanup authority is revoked independently of its retained lock handle.
3. Borrow the candidate's existing VFS-owned `HANDLE` via `SQLITE_FCNTL_WIN32_GET_HANDLE` on the lock-only file object; do not duplicate ownership or open a raw database alias. Perform same-volume handle-based rename through `SetFileInformationByHandle(FileRenameInfoEx)`, using the replace-if-exists and POSIX replacement flags for an admitted existing destination, and no replace permission for an expected absent one. This supplies replacement while old handles remain open; see [Microsoft's rename contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) and [the Win32 rename structure](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info). Keep the old and candidate VFS locks and exclusive namespace lease through rename, required durability and synced `InstalledPending`. Only then may candidate locking transfer/downgrade for checked reopen under the still-exclusive lease. Revoke obsolete pathname authority before lock-object teardown; old handles never clean up new-generation names.
4. Preflight the Windows build/OS/filesystem adapter's required handle-creation, rename and durability capabilities before retirement. The native publication acceptance target is desktop Windows on local NTFS with `FileRenameInfoEx` support, separately for bundled SQLite and SQLCipher; record exact OS/build/filesystem evidence. Do not infer publication support for remote shares or other filesystems from a passing NTFS test. A configuration without this protocol returns **`AcquisitionUnavailable(WindowsPublication)`** for `install_selected` and `publish_tmp`, before destination mutation; it does not try close-then-rename, raw copy/truncation or an unchecked rename fallback. Detected nonparticipating SQLite locks or sharing blockers are `Busy`, with rollback under the recorded move map if retirement already began. A possibly completed rename still uses installed/pending versus publication-unknown evidence. Keep Windows acquisition's path-type-only guarantee; these locks and handle operations do not add a Unix inode/swap-back proof.

Native Windows tests are mandatory for **both** `install_selected` and `publish_tmp`: first publication to an absent destination, replacement of an admitted regular destination, and a second publication after `Done`. Observe share/access flags and prove that the required old/candidate VFS locks and namespace exclusion remain held at the rename and durability seams. Include distinct old-WAL/new rows, a child-process lock contender, an incompatible non-delete-sharing handle, full teardown, and crash/restart points. Run bundled SQLite and SQLCipher. Unsupported-adapter controls assert typed refusal before retirement; they do not substitute for successful native publication evidence on the declared supported configuration.

### Installation and retirement of an old companion set

**A main-file rename is not the whole SQLite installation.** `install_selected` and `publish_tmp` use one shared publication primitive with these phases:

1. **Stage and request exclusion:** choose and retain the installation intent; obtain a checked consistent snapshot for a mutable source or retain a proven immutable source owner **before** copying, independently of this destination lease. Validate the synced, self-contained owned candidate, platform capabilities and complete namespace roles. For an immutable artifact, finish every byte-changing operation before assigning/verifying its expected publication digest, then prohibit further writable finalization. Retain the parent's admission gate while requesting the exclusive parent publication lease above. All shared-boundary connection/byte owners retain a shared parent lease for their lifetime, independent of the replaceable main inode. Those shared leases protect names, not source transactional consistency. The durable role ledger refuses a main/companion or installation-namespace conflict before mutation. Equivalent spellings use the same logical claim and state directory, with their complete literal companion families proven equivalent. Never admit without these gates/roles or unlink/recreate their locks while holders exist. Lookup must still create no files beside the original index. Process-local mutexes and main-name-only leases are insufficient.
2. **Quiesce, then complete exclusion:** an active writable connection/transaction holding the parent lease is `Busy`, with no retirement or publication; never forcibly checkpoint/close another writer. Drain the operation's own statements and closes through the lifetime policy. To preserve `regression_reader_survives_writer_full_build`, registered in-process read-only holders may first move under their connection mutexes to admitted private SQLite snapshots of their old logical database, then release their shared parent leases. Their exposed sources keep returning snapshot N. This is a coordinated snapshot transition of an admitted regular database, never a fallback after refusal. Complete exclusive lease acquisition only after shared holders have drained; do not deadlock waiting on the operation's own readers/staging. If a holder cannot be drained/snapshotted, or another process holds a lease, return `Busy` before changing the destination. Also require an exclusive publication lock through the checked SQLite VFS file object on an existing nonempty regular destination, without schema initialization or journal recovery; this permits replacing a corrupt regular cache while detecting nonparticipating SQLite locks. Inability to establish the lock is `Busy`. A zero-length placeholder is admitted by identity without SQLite initialization. Preserve the underlying automatic/POSIX locking choice. Windows uses the rename-compatible old/candidate VFS objects specified above. Do not simulate the lock by opening/closing a raw alias or release it before replacement. Concurrent arbitrary SQLite clients that bypass namespace exclusion cannot be promised rename-safe behavior; such concurrent external use is unsupported, and a detected external lock is never ignored.
3. **Record and retire:** under the lease and SQLite lock, revalidate the main and every literal `-wal`, `-shm`, `-journal` name. Use the discoverable sibling namespace `<destination>.ratarmount-install-state/` for **index-installation bookkeeping only**. Exclusively create it on first use; later reuse requires validated namespace ownership and records. Each new installation exclusively creates a fresh `<installation_id>.record` and owned retirement subdirectory without altering prior `Done` records. An unexplained collision refuses. The synced record contains the installation ID and intent, main/candidate identities and candidate digest, the immutable artifact's expected publication digest when applicable, and every old companion's identity/absence and unique retirement name. The durable logical-main role also enforces immutable-artifact restrictions across later opens. The entire move map is durable before the first companion moves. Close/poison old SQLite pathname cleanup authority before moving names; retaining a lock descriptor does not authorize later cleanup. Move every admitted old companion into that operation's retirement subdirectory by guarded rename, checking each identity immediately before its move. Retire the complete set and sync both directories **before** publishing the candidate. Do not copy old companions into the new database or unlink a symlink encountered in either namespace. New opens are barred by the lease/pending record while the old set is detached.
4. **Publish:** revalidate destination absence/identity and the absence of destination companions, guarded-rename the synced candidate over the main, and sync the parent. The installation record already identifies the candidate if the process dies immediately after rename. Durably record proven `InstalledPending` before any reopen. **Only mutable-index intent may perform subsequent writable finalization or enable WAL/change its staged digest. Immutable-artifact intent must preserve its exact expected bytes through verification, read-only reopen and teardown; `InstalledPending` grants no exception.** Expose no caller SQL before `Done`. Retain the lease and old/new managed locks until publication is durable and the retired generation has no cleanup authority over new names. Reopen only through shared checked acquisition with the intent and token for this installation.
5. **Complete durably or retain pending:** after durable main publication, intent-appropriate checked verification (including exact digest/no-companion checks for an immutable artifact), owned retirement cleanup and revocation of old-generation cleanup authority, durably transition **that installation's own record** to `Done { installation_id, outcome: Installed }`, syncing its namespace before releasing exclusion or returning ordinary success. Both `install_selected` and `publish_tmp`, including immediate reopen, use this transition without downgrading immutable intent. Before publication, exact old-main/moved-companion evidence may permit complete synced restoration; record `Done { outcome: RolledBack }` before admitting the usable old set and return the original uncommitted failure. Incomplete restoration stays recovery-pending. Never restore old companions beside a published new main. A sync, verification, close, cleanup or terminal-record failure returns structured **installed, maintenance-pending** when publication is proven, or index-publication-unknown when indeterminate. Preserve the last durable intent and evidence; no fetched-path fallback, unrelated installation or unowned cleanup.

**Admission and later publication:** under the parent lease and validated roles, inspect the namespace's installation records without following links. Validated `Done` records are historical terminal bookkeeping: ordinary checked lookup/open proceeds without recovery writes, retaining any immutable-artifact role/digest restriction. Later healthy writable changes to a **mutable working index** do not invalidate historical records merely because an old candidate digest differs; this does not permit drift in a hash-addressed artifact. `Done` grants no authority over current files; ordinary nofollow, identity and companion checks still apply. An unfinished/uninstalled or maintenance-pending installation yields `InstallPending` or index `PublicationUnknown`; malformed/foreign records and unsafe collisions refuse. At most one unfinished installation is allowed under the exclusive parent lease; unexpected multiple unfinished records require recovery, never a guessed newest record. Explicit recovery reconciles the pending installation under exclusive exclusion; only its token admits its proven old/candidate set and its recorded intent.

Retain prior `Done` records byte-for-byte. A later publication allocates a new installation ID and syncs its own preparation/move map before mutation; it does not replace or delete a completed record, use a latest-overlay receipt, or clear earlier identity evidence. Crash recovery observes the retained terminal records plus any unfinished new installation. No pruning/compaction of terminal records is introduced in this slice. Phase updates use synced temporary-record replacement and directory sync **only within the same unfinished installation**, followed by its terminal `Done` transition.

For an unfinished record without durable publication evidence, compare the recorded old main versus candidate identity/digest: proven old main permits exact restoration, proven candidate permits finishing without old companions, and indeterminate evidence refuses. With durable `InstalledPending` for a **mutable-index** installation, expected admitted new-generation WAL/finalization changes do not justify restoring the old set or requiring the initial staged digest forever. For an **immutable-artifact** installation, its exact expected digest and companion-free contract remain mandatory in every phase, including `InstalledPending`, `Done`, recovery and later ID resolution; changed bytes or new companions are a refusal, never expected finalization. Re-admit only the proven installed generation with its recorded intent and finish remaining index actions. Temporary-name absence alone is not publication evidence. Retirement cleanup checks the guard's current identities, including on teardown; leave a replaced retirement name intact.

**Separation from overlay security state is mandatory.** Installation IDs and `Done` records describe SQLite main/companion retirement only. They contain no overlay-delta replay key or consumption authorization. Their creation, completion, retention, recovery or later publication cannot clear an overlay record, release a required-identity latch, mark an overlay delta applied, authorize raw-directory commit, skip hashing/sealing, or replace existing archive/journal replay evidence. An index may be rebuilt without changing any of those decisions. No new overlay/commit receipt is created by this protocol.

Required controls include distinguishing old committed WAL rows and new candidate rows, active local/child writers and readers, and failures/crashes at every move, rename, sync, reopen, cleanup and terminal transition. Fresh lookup after `Done` sees only the candidate; a second publication succeeds with a new installation ID while the first `Done` remains unchanged. For immutable artifacts, separately prove that exact bytes still hash to their content ID after every verification/reopen/teardown/recovery seam; a second content ID names its own artifact. Restart finishes only an unfinished installation with its recorded intent, never replays an overlay commit or old WAL. Complete rollback admits the usable old set. Preserve live-reader snapshot and WAL/shm-generation pins, plus independent overlay identity/journal evidence across both installations.

### Reserved state directories are outside content identity

Reserve only the index-installation sibling-name suffix **`*.ratarmount-install-state`**, with a nonempty target stem. No new commit-state suffix or overlay replay namespace is introduced. Use one shared component predicate for identity, payload membership, serving and mutation protection. Match the suffix token ASCII case-insensitively, consistent with existing overlay bookkeeping protection, and cover filesystem-equivalent entry spellings; do not rely on lowercasing the complete path. A shared entry-aware classification must exclude each reserved directory entry **itself and its entire subtree**, before adding a directory node, hashing its metadata, deciding payload membership/empty directories, or recursing. Apply it in both `weak_walk` and `directory_digest_excluding`, bundle packing/manifests, every raw/database-backed overlay payload scan including `walkdir_files_and_empty_dirs`, and `overlay_changes.rs` `walk_host_entries`, non-Unix `walk_host_paths`, and `mentioned_paths` / row-only metadata mentions used by seal, fsck and diff. Extending the existing non-directory `is_ratarmount_sidecar_name` alone is insufficient. This exclusion applies only to owned index bookkeeping, not to existing overlay identity records or their required-record checks.

This suffix rule does not admit global coordination inside content: the actual resolved `ratarmount/coordination-v1` tree must pass the disjoint-placement contract above before any scan or source is admitted.

This content exclusion depends on the reserved entry name, not a live owner, a complete/valid record, successful recovery, or the target/index still existing. It therefore covers empty crash leftovers, partly written records, retired companion subdirectories, pending installations and retained index-installation `Done` records. Classify reserved names before file/directory dispatch; exclude a file/link collision from content without following it or enumerating descendants. Ownership/type/record validation remains the coordinator's separate admission gate: exclusion never authorizes adopting, deleting or recovering a collision; an unsafe entry or corrupt record at a required namespace still refuses there. Names merely resembling this exact reserved suffix remain ordinary content. This reservation is also enforced on mutations and preexisting payload collisions below; documentation alone is insufficient.

Directory-base reopening must pass its existing weak/strong base gate with these bookkeeping entries present, then reach the appropriate recovery coordinator without `--force-base-mismatch`. Preserve and extend `regression_index_publish_and_rotate_inside_directory_base_keeps_reopen` and `regression_sidecar_predicate_covers_every_writer_output`: exercise active, completed and empty/partial crash leftovers of the installation namespace, with weak/strong digest equality, normal overlay reopen, and absence from bundles/manifests/commit payloads. Retain controls proving real content changes and nonreserved look-alike directories still change identity and are included.

### Reserved state serving, mutation and cleanup protection

**Reservation must be enforced before clients can successfully write data that a later scan would omit.** Extend `is_overlay_internal_name` / `is_overlay_internal_path` with the shared component predicate. Apply it at every depth after path normalization, to both source and destination operands, including host-resolved traversal into a reserved entry through an alias. Keep the existing confinement/nofollow checks. Source lookup/list/cheap-list/search/versions/open and metadata/xattr reads hide reserved state through the same internal-name policy; full-path adapters cannot bypass it by naming a descendant directly. Coordinator artifacts are not exposed as archive/overlay members by any frontend.

Every user mutation into, of, or across a reserved component returns `PermissionDenied` with a reserved-bookkeeping diagnostic **before** copy-up, `create_dir_all`, host mutation, row/tombstone/accounting changes or descriptor handoff. Cover create/mkdir/mknod, open for write/truncate, writes through registered handles, unlink/rmdir, rename source and destination, hardlink/symlink destinations and alias access, chmod/chown/utime, and xattr changes. No user handle to a reserved entry is issued. Existing handles/paths must be revalidated when a coordinator establishes protection. Implement this in the shared overlay/source layer and existing mutation guards, including `open_overlay_fd_with_mode` and `rename_inner`; frontend handlers preserve the existing permission-denied mapping rather than adding route-specific name checks.

Before admitting a mutable overlay or successfully committing, sealing, diffing, fscking or bundling its payload, inspect reserved entries without following links. A preexisting user file/directory/link or row-only payload claim at a reserved name is an explicit reserved-name collision, not silently omitted successful payload. Require coordinator ownership/record evidence for operational use; unowned empty/partial leftovers receive recovery/collision instructions and remain untouched. Document that these newly reserved names cannot be used for user content and must be relocated before the operation can succeed. Do not auto-adopt or auto-delete a collision.

**Upgrade ordering is explicit:** run a read-only collision preflight over the directory base, overlay host entries and recorded payload mentions **before recomputing/comparing either stored weak or strong base digest**, including `overlay_meta::verify_base_path` and mount/reopen gates. An older recorded digest may legitimately include a newly reserved-looking user entry; unconditional exclusion would change that digest. Detect the collision first and report relocation/recovery instructions, preserving content and stored metadata. Do not first emit base mismatch or recommend `--force-base-mismatch`, rewrite the stored baseline, or use force to adopt the entry. An unreadable preflight refuses. Valid owned bookkeeping stays excluded and reaches the existing base/recovery gates normally; this diagnostic ordering does not waive genuine base changes or owner/sealed checks. Test legacy recorded weak and strong digests containing the installation-state suffix, including directory, file/link and row-only cases, with unchanged content and no force suggestion.

Protection also covers **ordinary ancestors containing a namespace**. Under the overlay's existing mutation/commit serialization, preflight a directory operation's affected subtree without following links. Refuse rename/move, replacement, recursive removal, ancestor tombstoning, or host metadata changes that would make protected state inaccessible. This includes moving a plain directory out of the tree or over another directory with nested state; checking only the operand's textual components misses it. Inspection failure refuses before any partial mutation. Ordinary sibling-file operations and virtual metadata changes that cannot affect coordinator access retain their behavior.

Coordinator namespace creation/maintenance inside a mutable overlay must participate in that containing root's operation guard and live commit-gate serialization, with an explicit coordinator token, as well as index/target exclusion. It may not race a reset or ancestor preflight. Without a validated containing-root guard, refuse that placement before creating the namespace and require an external state/index location. The token authorizes only that operation's owned artifacts and recorded transitions; a user path, matching suffix, PID or terminal installation record does not confer mutation authority. The shared index boundary also refuses a user-selected index path entering a reserved component without a token for that exact owned artifact, so an explicit `--index-file` cannot overwrite a record/lock through a different route. Read-only scanned directory bases still use the unconditional exclusion and ordinary coordinator ownership checks.

`reset_overlay_contents`, `account_reset`, `reset_overlay_dir`, live forget/prune and error/drop cleanup must preserve state and its stable locks. Before a public reset changes **any** host entry, queued operation, database row or accounting, preflight the complete tree under the root guard. Any pending/unknown operation, corrupt/unowned namespace or uninspectable protected subtree returns `Busy`/recovery refusal with no reset effects. A reset with validated terminal installation records may remove ordinary payload selectively, but must keep the namespace, record/lock identities, and necessary ordinary ancestor directories and access metadata. Never call `remove_dir_all` on such an ancestor; walk without following links and remove only unprotected entries. Document the retained ancestor directories. Live consumption likewise never prunes an ancestor containing state. Only the owning index coordinator may clean its proven staging/retirement artifacts after completion; terminal records remain retained. Reset cannot clear existing overlay identity/replay evidence or release durable namespace-role claims.

Apply that preflight explicitly to failure cleanup in `ratarmount/src/overlay_import.rs` and `ratarmount/src/overlay_upperdir.rs`, **before their `unseal` as well as `remove_dir_all`**, and to overlay teardown in `ratarmount-csi/src/process.rs`. An entire destination may be unsealed/removed only under its validated root/ownership guard after proving it contains no protected namespace, including one introduced after destination creation. A newly created or driver-private directory alone does not prove this. Otherwise retain protected state and ancestors, use selective cleanup only where the rules above permit it, and return/report the cleanup/recovery condition with the original failure. Do not chmod protected access metadata, clear rows, or discard evidence to make a failed command clean up successfully. The global-tree overlap refusal also applies before any such cleanup, without removing an existing conflicting tree.

Required regressions cover the installation-state suffix, case variants and multiple nested ancestors: denied create/write/truncate/rename/link/unlink/rmdir/metadata/xattr and direct descendant access; ancestor move/replace/delete/inaccessibility; user-file and row-only collisions; normal sibling/look-alike controls; reset with pending records, retained installation `Done` records and existing overlay identity evidence and corrupt/partial state; and live pruning. Assert unchanged record/lock identities, payload/rows/accounting on refused mutations, preserved nested installation records and existing identity evidence after successful selective reset, and restart reaching the same pending installation without modifying overlay replay decisions. Force failures in both import commands and CSI teardown with protected nested state; assert refusal/preservation before unseal/wipe, plus successful cleanup of an exclusively owned namespace-free destination. Include a coordinator-creation versus ancestor/reset race under the shared guard and at least one real writable SFTP/NFS/FUSE request through the common source protections. Out-of-band nonparticipating host mutations remain outside the coordination promise.

### Seal, reseal and unseal permission walks

An owned installation namespace, its records/locks and every descendant retain their validated coordinator permissions and identities during successful seal, reseal, unseal and failed-transition rollback. They acquire no payload mode rows. Rollback cannot rediscover them through a different traversal or widen their permissions.

Under the existing overlay root/seal-commit guard, preflight the whole affected tree before any permission, seal-row or sentinel change. **An active, pending/unknown, corrupt, unowned or uninspectable installation namespace blocks seal and reseal, and also blocks ordinary unseal/permission transitions**, with `Busy` or the structured installation/recovery refusal. Read-only inspection of terminal state after sealing and subsequent explicit unseal/reopen must remain possible without changing protected bytes or permissions.

Required successful seal/reseal/unseal tests place validated terminal state under multiple ordinary ancestors, including the root case, and compare record/lock bytes, identities and exact coordinator modes before and after each operation. Verify normal sealed payload permissions, seal/verify digest agreement, ancestor traversal, explicit unseal and fresh-process index admission/recoverability. Pending/unknown/corrupt/collision controls refuse before any mode/row/sentinel mutation; a permission-transition versus coordinator-creation race must serialize safely. ### Platform and embedding decision

**Decision: fail closed with a distinct `AcquisitionUnavailable` error when checked acquisition is unavailable. There is no portable raw-open or pathname-only Unix fallback in this plan.** This explicitly extends the documented overlay-only availability restriction to selected on-disk indexes, including read-only indexes and byte/install intents. It is a compatibility change requiring release notes and library/embedding documentation.

| Environment | Required behavior |
| --- | --- |
| 64-bit little-endian Linux glibc or macOS, x86_64/aarch64, installed intact hooks | Checked acquisition with #239 descriptor/reuse verification and the locking choice below. |
| Verified ABI but constructor abstained, private initialization unavailable, or hooks replaced | Terminal `AcquisitionUnavailable` carrying the installation reason; no repair/reinstall during an open and no fallback. Includes embedded/multithreaded hosts. |
| musl, BSD, 32-bit, big-endian, and other unsupported Unix ABIs/platforms | Terminal `AcquisitionUnavailable(UnsupportedAbi/UnsupportedPlatform)` for selected disk indexes, even regular files. Explicit no-persistent-index operation may still work if the underlying operation supports it. Never switch automatically after refusal. |
| Windows | Keep `open_checked`'s regular-file/path-type-only acquisition and before/after nofollow checks, with the checked handle-creation/cleanup adapter above. Same final-symlink refusal and diagnostic; no claim of Unix inode or swap-back proof. Publication additionally requires verified rename-compatible VFS handles and supported handle-based rename/durability; otherwise `AcquisitionUnavailable(WindowsPublication)` before retirement. Successful native first/second-publication evidence is required for each declared supported SQLite/SQLCipher configuration. |

Report symlink refusal if the final name is a symlink even when hook availability also fails; a regular path on that host reports unavailable acquisition. Test both outcomes. Supported Python/private-SQLite initialization keeps its existing early installation rules; no new late global initialization is introduced. Update `docs/sandbox.md` and affected embedding docs with this matrix, rather than leaving the old overlay-only restriction.

## Typed failures and recovery classification

Define a small shared error payload in `ratarmount-core` so `ratarmount-index` and every `MountSource` adapter can use it without a dependency cycle. It carries the requested index path, operation, offending name when different, and a stable reason: `Symlink`, `UnsafeType`, `IdentityMismatch`/indeterminate acquisition, `NamespaceConflict` with both mains/name/roles, or `AcquisitionUnavailable` with its reason (including `CoordinationStorage`, `NameEquivalence` and `WindowsPublication`). `IndexError`, format/session errors, discovery errors, and commit errors retain this payload and error source; an `io::Error` bridge embeds the payload, rather than just its display string.

The symlink diagnostic is exactly:

```text
refusing to rewrite symlinked index '<path>'; pass the real path via --index-file
```

Use the same wording for read-only refusal for consistency with the locked diagnostic. Additional companion/operation context may accompany it. Unavailable acquisition has a different diagnostic identifying platform/host/installation failure; changing `--index-file` cannot cure missing hooks. Never infer classification by matching diagnostic text.

These are **terminal acquisition failures**. Audit every catch, `Option`, bool, `.ok()`, `is_ok_and`, `unwrap_or`, and string conversion on the inventory's call graph. Terminal failure bypasses cold rebuild, another index candidate, in-memory/spool fallback, remote fetched-path fallback, cache invalidation/deletion, and best-effort log-and-success behavior. In particular:

- Nested durable loading must not turn refusal into `Ok(None)`: remove `try_load_nested_durable`'s `!path.is_file()` and generic-open-error short-circuits. Remove the following `exists()`/metadata gates in factory `open_tar`, `open_tar_gzip`, `open_tar_body` and `maybe_discard_index_below_minimum`, and `load_seek_state`'s non-read-only error-to-`Ok(None)` shortcut.
- Session `check_recreate_never` and `open_catalog_for_policy` must not report absence before shared classification, and `will_cold_build` must propagate terminal failures rather than classify every `open_lookup` error as a cold build. Replace `map_factory_error`'s display-text classification for acquisition causes with typed matching. Audit the named format `open` methods' `ip.exists()` plus log-and-rebuild paths. A dangling selected-index symlink with `--no-recreate-index` must return the locked symlink diagnostic, not `NotFound`.
- Compression side-table writers and digest-cache helpers, including `archive_digest_cache_available` and hashing-lock acquisition, become fallible and propagate terminal failures instead of logging and succeeding. Digest availability is not an ordinary open/drop of the old support name, and lock failure never permits an uncoordinated hash.
- `try_install_remote_index` and its callers return a fallible used/not-used result; refusal is not `false` and must not call `drop_fetched_sidecar` on an unowned/refused input.
- `invalidate_stale_commit_sidecar` must distinguish malformed/stale regular indexes from refusal; refusal is never authority to delete.
- Format probing, automount reader-to-spool retries, union fallback, and frontend caches must not turn refusal into absence or use another source to hide it.

Genuine absence, format mismatch, stale fingerprints, and ordinary corrupt-cache outcomes keep their existing recoverability **only after shared admission established that they are not terminal acquisition failures**. SQLite busy/corruption does not become a symlink error by default. Both the typed reason and whether the archive has committed must survive conversion; those are separate properties. Classification through `OpenBase` / `ClassifiedBase::open` must preserve acquisition failures too; an opener error cannot mint a weaker identity token or select the raw-directory API.

Installed/committed maintenance-pending and publication-unknown results retain their structured operation state alongside the cause; they are never an ordinary cache miss or a boolean “not used”. Prepared-companion classification must report symlinks before `Leftover`/incomplete-preparation classification. Adapters match the typed payload before legacy errno reduction: preserve the existing raw-error/`ENOSYS` pins while returning typed unavailable acquisition as `EOPNOTSUPP`. NFSv4's fabricated absent `FileInfo`, 9P's optional walk, NFS `.ok_or` and version-path probe fallbacks must all preserve `Err` after the discovery migration.

Expose unfinished installations as `InstallPending { installation_id, publication_state, cause }`, retaining whether the main is proven uninstalled or installed. Indeterminate index publication is `PublicationUnknown { installation_id, cause }`. Carry these structured installation outcomes through `SourceError` and I/O bridges as well as commit APIs; do not erase them to the nested cause or reduce them to absence. A terminal installation `Done` record is neither outcome. For archive commits, preserve the existing publication/committed classification and attach the typed acquisition cause without allocating a new durable commit ID or replay receipt.

## Fallible discovery and wrapper migration

Change the canonical discovery API in `ratarmount-core` before migrating its consumers. This is a source-level library API change, documented with migration notes. No parallel infallible discovery path may remain in production that can hide a lazy acquisition error. Illustrative signatures:

```rust
lookup(path, file_version) -> Result<Option<FileInfo>, SourceError>
list(path) -> Result<Option<ListResult>, SourceError>
list_with(path, need) -> Result<Option<ListResult>, SourceError>
list_mode(path) -> Result<Option<ListModeResult>, SourceError>
list_dirents(path) -> Result<Option<Vec<CheapDirent>>, SourceError>

exists(path) -> Result<bool, SourceError>

search_cheap(pattern) -> Result<Option<Vec<CheapSearchHit>>, SourceError>
```

`SourceError` retains the typed acquisition payload and ordinary I/O causes. `Ok(None)`, `Ok(false)`, or zero versions preserve their existing absence/unsupported semantics; `Err` is never absence. Preserve the cheap-list/cheap-search distinctions. Any additional optional helper that can acquire an index must also become fallible. Existing `open`/`read` I/O results retain typed failures through their error bridge.

Migrate export-core and each protocol's metadata, directory, version and existence helpers as well as file opens. Include search/control helpers that can open the selected index.

Automount's nested reader/path acquisition returns `Result<Option<...>, SourceError>`; `ensure_lazy_mount` and `ensure_lazy_children` become fallible. Terminal failure from the reader path cannot trigger a spool/path retry. Failed acquisitions never enter the successful mount cache, and repeated requests preserve the refusal while the index remains refused. Eager discovery fails before service startup when it reaches such an index.

Keep dispatch to the mounted nested source for **all** `file_version` values, including nonzero/negative selectors. `FileVersionLayer::decode` and its probe lookups become fallible too. For `/inner.tar/member.versions/1`, the first request can call `open_nested_tar_with_durable` -> `try_load_nested_durable` -> `SqliteIndex::open_lookup_for_open(ctx.outer_index_path)`, then select row version 1 in the nested source. The durable catalog acquisition is in the outer selected SQLite file; the member lookup must still dispatch to the nested archive. `.versions` enumeration uses fallible `versions` on that same nested source. Do not add a supposed per-version SQLite opener or a newest-only preparation check in `versioning.rs`.

## Frontend surfaces and concrete triggers

Initial mount/factory refusal is a CLI/library error **before bind/listen, FUSE mount, or export registration**. A top-level selected-index symlink present at startup therefore has no HTTP URL. Frontend request tests below start with a valid top-level source and cause a later acquisition.

All adapters inspect a structured pending/unknown outcome first, then the shared typed acquisition failure before reducing it to errno/status. Where a protocol has no text field, emit the full diagnostic in the server log and return the status on the wire. Other ordinary errors retain their current mappings.

Startup CLI failure remains nonzero. Post-publication commit failure uses the committed outcome below rather than the ordinary startup exit. PROPFIND `/inner.tar/member` (Depth 0), `/inner.tar/` (Depth 1), or `/` with child discovery then reaches `try_load_nested_durable` and its fresh `open_lookup_for_open` of the refused outer index. ## Commit integration preserves main's identity and recovery policy

Offline/live metadata/provenance, append, zstd splice, ZIP/copy replacement, raw-directory, rolling initialization/rotation, idle/on-exit and current remote routes use one operation-owned `CommitIndexAccess` context for their selected indexes. It delegates to the shared boundary and owns checked connections through teardown. It covers every sidecar the chosen route patches, invalidates, installs or removes, including sibling/default-folder selections and not-yet-created rolling targets. **It is an index-access context, not a new overlay transaction or receipt protocol.** Its presence, absence and index `Done` state cannot select an overlay identity mode.

### Prepare index access before caller mutations

Retain the existing classified-base, sealed/lower, required-record and journal-owner checks, operation guards, archive locks and locked-stamp rechecks. Prepare shared index access before archive mutation, destructive stale-index cleanup, caller-side journal recovery or missing-archive initialization. Passing these index checks is necessary for selected-index work and never substitutes for any existing overlay/archive check. Keep main's lock ordering and pass held guards through helpers rather than reacquiring their file locks through independent descriptors.

`sidecar_path_for_patch` becomes fallible admitted optional state, not an `is_file()`-filtered pathname. Remove existence and generic-error bypasses. A genuinely absent optional sidecar remains absent; do not create it merely to patch. Admit uncompressed-append sidecars outside the closure whose failure can choose `copy_after_failed_replace`; a terminal refusal never selects Auto-copy, another index candidate or raw-directory fallback.

Move CLI `main.rs` raw-directory `recover_journal_at` and `overlay_commit::maybe_create_missing_write_base` into the same prepared sequence exposed by `OverlayCommitGuard` to CLI/library callers. For a new attempt, a preexisting selected-sidecar refusal leaves the interrupted archive/journal or absent archive, baseline, overlay payload/rows and links/targets unchanged. Existing journal authorization is rechecked on the locked archive, and successful recovery retains main's baseline restamp-before-journal-unlink ordering. A required record cannot become optional because the index was refused or rebuilt. `--force-base-mismatch` retains its existing limited meaning and cannot override selected-index policy, sealing or required-record protections.

Startup recovery that does not acquire or mutate a selected index keeps its existing mainline recovery policy; part 2 adds no new archive recovery record. Any subsequent selected-index open must still refuse before mounting/listening. Do not relabel an already committed or unresolved existing journal operation as uncommitted merely because a fresh index open fails.

### Rolling targets: select, admit, then create/open

Split `rolling_commit_target` / `RollingMountSource::prepare_commit` into read-only target selection and initialization/open using the selected token plus shared index access. Apply the same ordering to `with_clock`/empty-series startup. Use the existing commit serialization and delta preview to retain current size/time buckets, empty-tick behavior, generation rules, metadata/delete deferral and default index naming. Selection must not create an archive, advance the active member/union, refresh the baseline or consume overlay entries.

Resolve and admit the chosen generation's complete sidecar/companion intents while its archive can still be absent. Revalidate immediately before initialization and carry the admitted context into the factory opener; an opener called only after creation is too late. Refusal leaves the chosen archive absent, the prior active generation/union/baseline intact and the delta retained. Do not skip to another generation to evade refusal.

This split adds no persisted series operation, frozen delta, generation-completion receipt, or multi-process replay protocol. Existing creation, publication, remount and journal-recovery guarantees remain on main's terms. Do not claim new exactly-once behavior across rolling crashes. If safe index-before-creation ordering cannot be achieved within that boundary, return the specific conflict to architecture review rather than adding overlay receipts.

### Preserve committed outcomes and stop unsafe retries

Preserve the typed selected-index cause alongside whether the existing archive operation is known uncommitted, known committed, or unresolved by its available publication/journal evidence. Extend error transport where current string conversions lose those facts. A late index failure after proven archive publication is reported as committed with index maintenance failed, never as permission to rerun the archive delta. An indeterminate existing outcome remains recovery-required; index admission alone cannot decide it. Do not manufacture a new operation ID or durable replay record to transport an error.

For a proven late committed refusal, CLI exits 1 with “archive committed; index maintenance failed”, the typed diagnostic and existing recovery/remount guidance. Keep the committed baseline/restamp required by main; never restore an earlier baseline to pretend publication failed. Live mounts invalidate stale reader/inode caches and retain the existing failed-source safety behavior; discovery through a failed source returns its stored error, not absence. Preserve interval warning scheduling. Automatic retries must not re-enter archive persistence merely to retry refused index maintenance. Use only an existing safe recovery/maintenance path with its identity checks; otherwise stop and require recovery/remount, retaining available evidence and payload.

Remote archive upload and index/blob/pointer maintenance remain distinct outcomes. Route selected-index snapshot/read/install operations through the shared boundary and retain their typed failures even where a callback currently logs `PointerRefused`. If the archive is already published, do not upload/resplice it to recover from an index refusal. If existing backend evidence cannot resolve publication, preserve uncertainty and refuse automatic replay. This plan adds no remote conditional-write semantics, persistent replay spools, cross-client guarantees or overlay receipts.

### Retention, raw directories, hashing and sealing stay unchanged

Successful offline TAR/ZIP/compressed/provenance commits retain overlay payload files, directories, database rows and tombstones with the existing removal guidance. Existing live routes keep their current guarded forget/prune semantics, including protection of pending edits and protected index bookkeeping. Part 2 adds no consumption-policy enum, durable edit revisions, delta snapshots or new retained-overlay replay semantics. Do not use an index failure or installation completion to reset/forget overlay state.

A genuinely raw directory continues through main's explicit raw API, remains database/marker-free and honestly reports `identity_checked: false`. The existing absence, lost-record/marker and journal-owner checks still decide whether that API is allowed. A classified/recorded overlay cannot become raw because another operation, index rebuild, `Done` record or cleanup lost its evidence. This preserves the current raw API; it does not claim newly added exactly-once replay protection for unrecorded raw payloads.

Keep the existing weak/strong base checks, strong digest/pending rules, hash guard semantics, immutable/prepared restrictions, sealed/lower checks and locked recovery authorizers. New index-bookkeeping exclusions must not hide real payload changes, suppress a required identity row, mark a pending digest valid, or authorize unseal. Digest-lock relocation preserves the effective hashing checks and real exclusion; it cannot be treated as an identity reset.

For protected A → B → retry A, A's identity/replay evidence must remain effective or A must pass a fresh identity check. A retry with `identity_checked: false` due to B replacing a receipt is forbidden. No new overlay/commit receipt, receipt removal, or latest-receipt lookup remains in this plan. Any future proposal that participates in that decision is a separate architecture change subject to this same non-waivable invariant.
